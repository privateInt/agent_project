# D29 v2: 요청 결합·claim 확인·실행 제한 보완
기존계획과clarifications를유지하며다음3개지적을정확히보완한다.
1. request_bytes는 UTF8 `json.dumps(value,sort_keys=True,separators=(',',':'),ensure_ascii=True,allow_nan=False).encode('utf8')`이며 exact keys schema1,role,thread_id,intent_sha256,settings_sha256,prompt,argv,local_token_scope='LOCAL_ONLY'이다. argv는문서화된CLI배열, prompt는원문그대로이며prompt_sha256은원문UTF8만hash한다. request_sha256은위canonical bytes SHA256이며자기hash필드미포함. owner binding exact keys schema1,role,thread_id,turn_id,user_message_item_id,observed_client_id,prompt_sha256,request_sha256,cli_receipt_sha256. CLIreceipt는canonicalresultrecord hash이며request hash와다르다. 응답유실로receipt없으면명시None만허용한다. C04에 request hash·user item ID·role 불일치거부,observed_client_id=None와실제null/누락의정상일치, clientId를다른ID로추정하지않는검사를추가한다. 실제binding값은발명하지않으며fixture만명시한다.
2. C01 임시새DB는 기존 initialize_intent_journal 결과reason JOURNAL_READY, commit_confirmed/closed 확인후만사용한다. reserve/read/claim 결과의정확reason과dbcommit/transaction_closed/new_claim을확인한다. COMMIT 전raise→실제rollback확인 PREPARED/adapter0; COMMIT 수행후확인raise→DB재조회 UNKNOWN/adapter0; 두case새connection재개방으로bytes/hash/revision을대조한다. UNKNOWN이저장됐으면그뒤재진입adapter추가0. 초기claim에서CLAIM_RECORDED/new_claimTrue/commit확인 모두있을때만1회진입. caller borrowed connection은계속usable이고close/init/migration0.

C01/C02 defaultsubmissiondisabled, 각temp root/user/localPAUSE, scheduleoutside, cap3, rootlockbusy, admit/checkpoint저장실패를독립새intent로구성한다. 모두CLI adapter0, UNKNOWN이면재진입0, 기존파일/DB유지. 환경제약은PR24 directory/read_file/lock/admit 및고정schedulepolicy를재사용한다. 실제root/user PAUSE는변경하거나읽기재검증하지않는다. 테스트는명시적인/tmpprivatefixture만사용하고실제CLI/socket/native0이다.
