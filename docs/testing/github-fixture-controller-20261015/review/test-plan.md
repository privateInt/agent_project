## Proposed contract for reviewer approval

Public functions remain exactly the three proposed in requirements: `initialize_fixture_controller(control_connection)`, `run_fixture_job(ledger_connection, control_connection, state_dir_fd, expected_assignment_sha256, assignment_bytes)`, `read_fixture_controller_job(ledger_connection, control_connection, job_id, expected_assignment_sha256)`.

The new control DB is separate from the unchanged ledger schema1. Proposed control application ID `0x41504643`, user_version1; one `fixture_controller_jobs` table with immutable `job_id`, `assignment_sha256`, state `CLAIMED` or `PREPARATION_FAILED` and nullable `preparation_reason`. Freeze exact DDL/constraints in the new contract before implementation. No CLAIMED deletion/reset/reassignment/lease expiry/retry API. Only `CLAIMED -> PREPARATION_FAILED` is allowed, guarded by job/pin/prior state and an allowlisted preparation reason.

Caller supplies two dedicated builtin SQLite connections; use the ledger's same connection prerequisites, including no caller transaction, no attached DB/temp objects, FULL/EXTRA synchronous, delete/memory journal and busy_timeout <=1000ms. Validate both connections before accepting work. Same connection supplied twice is rejected. Foreign schema is rejected; run/read never initialize, migrate or repair. Initializer touches only an empty dedicated control DB or verifies its exact schema. Existing transactions, flags and connection lifetimes remain caller-owned.

Run ordering: validate/assign through the original ledger API; read already stored artifact/control state; for a new job commit one conditional control claim; only the caller whose new claim COMMIT was acknowledged may call the collector once. No transaction/DB lock is held across collection. Existing claims without an artifact return outcome unknown and never collect again. A claimed job abandoned before collection is deliberately not automatically recoverable. This is at-most-one controller invocation, not exactly-once process execution or authenticated state origin.

A final valid artifact in the ledger confirms **storage**, including exit7/partial failure artifacts. Return its exact bytes/hash/binding on subsequent read/run without recollecting. A durable PREPARATION_FAILED row is terminal even when the supplied directory is later repaired. A PREPARATION_FAILED row plus a stored artifact is inconsistent state: block, preserve both, and never convert the terminal controller failure into successful execution. An orphan claim without its matching ledger assignment also blocks. Two DBs are not one atomic transaction; an assigned ledger row with no claim is an incomplete assignment, not evidence of execution.

Definitive preparation whitelist from the pinned collector is exactly `ARGUMENTS_INVALID`, `STATE_FD_INVALID`, `ASSIGNMENT_FILE_INVALID`, `ASSIGNMENT_HASH_MISMATCH`, `ASSIGNMENT_INVALID`, `REAL_EXECUTION_BLOCKED`. Persist a terminal failure only for a structurally valid pinned-collector response with artifact/binding None, one of those reasons and all no-child/no-output fields consistent with the actual `_report` contract. Do not classify by arbitrary text, `status=BLOCKED` alone, or artifact None alone. SPAWN_FAILED, IO_UNCONFIRMED, CLEANUP_UNCONFIRMED, UNEXPECTED_FAILURE, raised exceptions, malformed responses and contradictory report/artifact/binding are OUTCOME_UNKNOWN; keep CLAIMED. A valid non-None artifact must be accepted by original ledger validation before storage confirmation.

Claim COMMIT, failure-transition COMMIT and artifact COMMIT errors are distinct. Never infer an uncommitted write from a failed response, retry automatically, reset a claim or call the collector after an unconfirmed claim write. After failure-transition loss, independent read decides CLAIMED versus PREPARATION_FAILED. After artifact-record loss retain the originally collected bytes in the current caller result; independent read may confirm the committed original artifact. If it does not, remain unknown and never recollect.

Proposed result shape is exact `{report, record, artifact}`. `record` is the original ledger record or None; `artifact` is exact collected/stored bytes or None and must survive uncertain record storage. Do not expose raw data in report. Proposed fixed report keys: `scope,status,reason,control_state,preparation_reason,collection_reason,artifact_storage_confirmed,ledger_transaction_closed,control_transaction_closed,fixture_only,head_code_executed` plus the nine existing origin/trust/native/merge flags. Scope is `FIXTURE_CONTROLLER_ONLY`; all flags are strict bool, fixture_only true/head_code_executed false, all nine trust flags false. Status is OBSERVED only for CONTROLLER_READY/ARTIFACT_STORED; terminal failure/unknown/invalid input stays BLOCKED. Fixed reasons: CONTROLLER_READY, ARTIFACT_STORED, PREPARATION_FAILED, OUTCOME_UNKNOWN, DATABASE_UNCONFIRMED, ARGUMENTS_INVALID, CONNECTION_INVALID, SCHEMA_INVALID, ASSIGNMENT_HASH_MISMATCH, ASSIGNMENT_INVALID, ASSIGNMENT_CONFLICT, ASSIGNMENT_PIN_MISMATCH, REAL_EXECUTION_BLOCKED, JOB_NOT_FOUND, STATE_CONFLICT. Unrecognized exceptions/reasons map conservatively; no raw exception, job/target/hash/path/SQL in report. Transaction flags reflect each connection independently.

## Contract gaps to resolve in pre-review

1. Requirements did not fix result/report keys, reason vocabulary or control DDL/application ID. The proposals above make assertions reviewable; coordinator/reviewer must accept or revise them **before** implementation. Do not derive expectations from whichever implementation happens to appear.
2. Two caller-supplied DBs do not prove protected path/owner/origin, rollback resistance or a permanent ledger pairing. Pin/job checks prevent accidental conflicting records but not an owner with DB rewrite access. D35 coverage here is the supplied connection/input boundary; protected installation, separate UID/head isolation, signer roster and trusted issuer/gate remain NOT_RUN/out of scope.
3. With only CLAIMED/PREPARATION_FAILED, a failed claim transaction that left no row cannot encode a permanent tombstone. Conservative proposal: failing call returns unknown and does not execute; independent read is read-only; permanently non-retryable **committed** claims are enforced. If permanent refusal even after proof of no committed claim is required, a new durable intent state/API and failure model must be approved rather than claiming this schema supplies it.
4. A valid ledger artifact and durable terminal preparation failure cannot both be treated as execution success. Proposed STATE_CONFLICT preserves the artifact as storage data and the terminal failure, with no success/merge flags. Missing control state with a preexisting valid sealed artifact may return its storage confirmation without execution, but must not invent an invocation claim.
5. Separate connections mean no cross-DB atomic commit. The contract must explicitly tolerate a ledger assignment with no claim, retain claims through failure transitions/record uncertainty, and distinguish readback confirmation from automatic retries. C07-C10 provide this evidence; no exactly-once process guarantee is asserted.
