# 공통 테스트 기준

문서판: 1.3-preparation

[공통 규칙](RULES.md)과 [결정 기록](DECISIONS.md)을 함께 읽는다. 프로젝트의 실행 명령과 요구사항별 수치는 프로젝트 문서 및 구현 전 검사 계획에서 관리한다.

## 공통 검사 범주 — 확정 규칙 D28

이 절은 D27의 공통 검사 기준이다. 아래 범주를 기본으로 검토하고 수정한 언어·설정·기능과 영향받는 범위에 적용할 검사를 연결한다. 범주별 실행 명령·환경과 구체적인 수치 기준은 프로젝트 및 요구사항에 맞춰 정하며 아직 미확정이다.

| 검사 범주 | 확인할 내용 |
|---|---|
| 정적 검사·빌드 | 문법·타입·import 오류와 변경 대상의 빌드 가능 여부 |
| 변경 동작 검사 | 수정한 기능의 정상·오류·경계 조건과 확인 가능한 결과 |
| 회귀 검사 | 영향을 받는 기존 기능의 동작과 보존할 계약의 유지 |
| 구조·계약 검사 | API 규격과 모듈·플랫폼의 책임 경계 유지 |
| 기본 보안 검사 | 코드·설정의 비밀정보 노출과 의존성 취약점 |

- 이 목록은 검사의 상한이 아니다. 요구사항·변경 영향·발견된 실패에 따라 실제 연동, 권한, 사용자 흐름, 장애·복구, 동시성·중복 처리, 데이터 변경·복원, 성능, LLM 품질 등 필요한 검사를 추가한다. 영역별 구체적인 필수 조건은 별도로 정한다.
- 검사마다 연결 요구사항, 상황·입력, 기대 결과와 확인할 데이터, 필수 여부·통과 기준, 실행 환경·근거를 기록한다. 요구사항 원문과 공통 규칙은 기준 위치를 참조하고 중복 작성하지 않는다.
- 같은 검증을 제공하는 기존 검사를 우선 재사용한다. 추가·변경한 검사는 필요성과 기존 검사가 확인하지 못하는 범위를 설명한다.
- 적용 대상이 없는 범주는 이유를 기록한다. 문서만 바꾸는 작업 등에 적용 대상이 없는 경우와, 필요한 대상·검사가 있는데 환경 부족 등으로 실행하지 못한 경우를 구분한다. 기존 필수 검사를 적용 대상 없음으로 재분류해 범위를 줄이는 변경에는 D06을 적용한다.
- 필수 검사 판정과 기존 실패 분리는 D04~D05, 기준 변경의 중요도와 결정 권한은 D06~D07, test_agent와 reviewer의 책임은 D09를 따른다. 필요한 검사 추가를 기존 검사의 삭제·완화나 미실행 허용으로 해석하지 않는다.

## 구현 전 검사 계획 — 확정 규칙 D29

1. 주 에이전트는 작업의 요구사항 위치와 변경 영향을 연결한다. test_agent는 이를 바탕으로 필수 검사·상황과 입력·기대 결과와 확인할 데이터·통과 기준을 작성한다. 공통 기준과 프로젝트별 기준은 참조하고 기존 검사는 재사용한다.
2. 독립 reviewer는 계획이 요구사항과 변경 영향에 맞는지, 필요한 검사가 빠지지 않았는지, 기대 결과와 판정 기준이 명확한지 확인한다. 확인한 계획 버전과 검토 근거를 작업 기록에 남긴다.
3. 사전 검토를 통과한 뒤 해당 작업의 구현을 시작한다. 실제 테스트 코드는 구현과 병행해서 작성할 수 있다. 사전 기준 작성이 모든 테스트 코드의 사전 완성을 요구하는 것은 아니다.
4. 개발 중 필요한 검사 추가나 기준 변경은 이유와 영향을 기록한다. 중요한 기준 변경은 D06에 따라 사용자에게 판단을 요청하며, 모호한 경우도 같은 기준을 따른다. 사소한 변경은 독립 reviewer가 검토한다. 결정 대기 중 해당 변경과 의존 작업은 보류하고 독립 작업은 D08에 따라 진행한다.
5. 구현 뒤 실제 검사 결과와 소스·환경·근거를 계획의 기준 버전에 연결하고 최종 독립 검토를 받는다. 사전 계획 검토는 최종 구현 검토를 대신하지 않으며 완료·사용 가능·병합 판정은 D04~D07과 D20을 유지한다.

## 실제 연동 검사 — 확정 규칙 D30

- DB·큐·스토리지·서비스 연동에 영향을 주는 변경은 그 영향을 검증하는 실제 연동 검사를 필수로 둔다. D29의 사전 계획에서 대상 연동·상황·기대 결과·확인할 데이터·통과 기준을 정한다.
- 실제 검사는 격리된 테스트 환경에서 수행할 수 있다. 대상 구성요소의 실제 구현을 사용하고 사용한 버전·설정 참조·데이터 조건과 검증 범위를 기록한다. 운영 데이터와 비밀정보의 보호 기준은 유지한다.
- 가짜 응답이나 fixture를 사용하는 검사는 별도 근거로 남긴다. 일부 연동만 실제로 검증했다면 그 범위를 명시하고 나머지 필수 연동까지 통과한 것으로 보고하지 않는다.
- 응답 코드나 연결 성공 외에 요구사항이 정한 저장 상태·파일·작업 상태·메시지 처리 결과 등을 확인한다. 구체적인 확인 항목은 해당 요구사항과 계획을 따른다.
- 필요한 환경이 없거나 필수 검사를 실행하지 못했으면 해당 기능을 사용 가능으로 판정하지 않는다. D04~D05에 따라 결과를 구분하고 미실행 이유·필요한 환경·다음 조치를 기록한다. 독립 작업 진행은 D08을 따른다.
- 기존 필수 검사를 가짜 응답 검사로 대체하거나 선택 검사로 낮추는 등의 중요한 기준 변경은 D06~D07을 따른다. 실제 환경 구축·검사 명령·실행 권한은 프로젝트 설정 단계에서 확인한다.

## 실제 브라우저 E2E — 확정 규칙 D31

- 핵심 사용자 흐름에 영향을 주는 화면 변경에는 실제 브라우저 E2E 검사를 필수로 둔다. D29의 사전 계획에서 대상 흐름·사용자 행동·기대 결과·통과 기준을 정한다.
- 사용자 행동부터 최종 결과까지 확인한다. 예를 들어 문서 업로드 흐름은 업로드·처리 상태·결과 조회를 연결해 요구사항이 정한 화면과 실제 결과를 확인한다. 버튼 클릭이나 HTTP 성공 코드만으로 완료 판정을 대신하지 않는다.
- 실제 브라우저에서 서비스를 이용하는 근거와 가짜 DOM·응답으로 실행한 검사의 근거를 구분한다. 실제 연동에 영향을 주는 경우에는 D30의 검증 기준도 적용한다.
- 격리된 검증 환경을 사용할 수 있다. 테스트별 데이터·세션을 분리하고 정리 범위를 확인해 실행 순서와 공유 상태에 따른 영향을 줄인다. 운영 자산과 비밀정보의 보호 기준은 유지한다.
- 단순 문구·스타일 변경은 영향에 맞는 검사를 정한다. 변경 분류만으로 면제하지 않으며 핵심 흐름에 영향을 주면 이 절을 적용한다. 기존 필수 검사 범위를 줄이는 변경은 D06~D07을 따른다.
- 실제 브라우저 환경이 없거나 필요한 검사를 실행하지 못하면 해당 기능의 사용 가능 판정은 대기한다. D04~D05에 따라 결과를 구분하고 검증 환경·소스·검사 범위·근거와 미실행 이유를 기록한다. 승인된 독립 작업은 D08에 따라 계속할 수 있다.

## 비동기 작업의 장애·복구·중복 처리 — 확정 규칙 D32

- 비동기 작업·재시도 로직에 영향을 주는 변경은 장애·복구와 중복 처리 검사를 필수로 둔다. 검증할 작업·상황·복구 결과·상태 전이·재시도 한도·중복 처리 기준은 D29의 사전 계획에서 요구사항과 계약에 연결한다.
- 워커 중단, 타임아웃, 부분 실패 등 관련 장애 상황에서 정해진 정책대로 재개하거나 실패 처리되는지 확인한다. 성공하지 않은 작업을 성공 상태로 기록하지 않는지, 재시도 한도와 최종 상태를 지키는지도 해당 계약에 맞춰 검사한다.
- 동일 요청·메시지의 재전송이나 동시 처리로 의도하지 않은 중복 작업·결과가 생기지 않는지 확인한다. 의도한 반복 실행과 중복 요청의 의미를 구분하고 작업 상태·DB 레코드·파일·메시지 결과 등 요구사항이 정한 데이터를 검사한다.
- 위 상황은 검사 설계의 예시이며 실제 변경에 맞는 시나리오와 통과 기준을 정한다. 복구 정책이나 중복 허용 여부가 정해지지 않았다면 구현 결과에 맞춰 기대값을 만들지 않고 요구사항을 먼저 확인한다.
- 장애 검사는 격리된 검증 환경에서 계획한 대상과 범위로 수행한다. 실제 연동에 영향을 주는 경우 D30을 적용하고, 가짜 응답 검사의 근거와 실제 서비스의 검증 범위를 구분한다.
- 필요한 검사·환경이 준비되지 않으면 D04~D05에 따라 해당 기능의 사용 가능 판정은 대기한다. 미실행 항목·환경·검증 범위·근거를 기록하고 독립 작업은 D08을 따른다. 기준 변경은 D06~D07의 권한을 유지한다.
- 기능 자체의 재시도 정책은 해당 계약을 따른다. 이를 개발 중 자동 수정의 상한인 D17~D18이나 운영 적용 실패의 재시도 기준인 D21과 혼동하지 않는다.

## 데이터 변경·복원 검사와 백업 최소화 — 확정 규칙 D33~D34

- 데이터 구조·마이그레이션의 이행·보존 검사와 백업·복구의 실제 복원 검사는 reviewer가 변경별로 필수 여부를 판단한다. D29의 사전 계획에서 영향받는 데이터·호환성·복구 필요성과 기존 검증을 확인하고 검사 선정·생략 이유를 기록한다.
- 새로운 검사 계획의 선정과 기존 필수 검사의 완화를 구분한다. 이미 정한 필수 검사를 삭제·선택 전환하거나 범위를 줄이는 중요한 변경은 D06~D07을 따른다. D30의 실제 연동, D31의 핵심 화면 흐름, D32의 비동기 작업 검증과 D02의 데이터 삭제 제한도 유지한다.
- 백업 생성과 복원 검사는 서로 다른 작업이다. 백업을 매 작업의 기본 절차로 두지 않는다. 필요한 검사와 복구 수단을 정한 뒤 추가 백업이 필요한지 검토한다.
- 기존 백업이 변경 대상과 필요한 복구 시점을 포함하고 실제 사용 가능한 근거가 있으면 우선 재사용한다. 코드·문서는 확인된 Git 이력이나 격리된 복사본으로 복귀할 수 있으면 별도 압축 백업을 생략한다. DB·운영 데이터와 비밀정보를 Git 이력으로 복구할 수 있다고 가정하지 않는다.
- 복구가 필요한 변경에 대해 적절한 기존 복구 수단이 없으면 필요한 대상과 범위만 백업한다. 프로젝트 전체나 대용량 데이터의 반복 복사를 기본으로 하지 않는다. 실행 여부·이유·범위·복구 경로와 소요 시간을 기록한다.
- 이미 확인한 복원 근거는 대상·환경·복구 조건이 여전히 맞는지 대조해 재사용한다. 새 변경·실패·미해결 우려가 없으면 같은 복원 검사를 반복하지 않는다. 필요한 검증이 새로 생기면 관련 범위를 확인한다.
- 이 정책을 기존 백업의 자동 삭제나 필요한 복구 수단의 무시로 해석하지 않는다. 실제 보존 기간·정리 대상은 프로젝트별로 별도 정한다. 이 절은 규칙 설계이며 백업 생성·삭제나 복원 작업을 활성화하지 않는다.

## 권한·접근 제어 검사 — 확정 규칙 D35

- 인증·권한·사용자 간 데이터 접근·도구 실행 정책에 영향을 주는 변경은 허용·거부·격리 검사를 필수로 둔다. D29의 사전 계획에서 사용자·역할·대상 데이터·동작과 허용 조건을 해당 기능의 정책에 연결한다.
- 허용된 사용자의 정상 동작과 권한 없는 접근의 거부를 함께 확인한다. 변경 범위에 맞춰 미인증·만료된 인증·다른 역할·다른 사용자의 데이터 ID 등 관련 조건을 검사한다.
- 거부된 요청의 응답과 함께 보호 대상의 데이터·파일·작업 상태가 정책대로 유지되는지 확인한다. 공유를 허용하는 기능은 정해진 공유 범위와 거부 범위를 구분한다.
- 사용자 흐름과 서버 API에서 정책이 실제로 적용되는지 확인하고, 도구 실행에는 허용한 도구·대상·실행 범위의 준수를 검사한다. 실제 연동과 핵심 화면 흐름에 영향을 주면 D30~D31도 적용한다.
- 기존 공통 보안 검사를 재사용할 수 있는지 확인하고 D28의 기본 보안 검사와 연결한다. 테스트 계정·데이터와 검증 범위는 격리하고 비밀 값은 기록하지 않는다. 판정과 기준 변경은 D04~D07을 따른다.

## LLM·RAG 품질 평가 — 확정 규칙 D36

- 모델·프롬프트·검색·도구 선택 등 LLM/RAG 결과에 영향을 주는 변경은 품질 평가를 필수로 둔다. D29의 사전 계획에서 평가 대상과 연결 요구사항, 고정 질문·문서·기대 근거와 판정 기준을 정한다.
- 검색 근거, 답변의 핵심 사실과 인용 근거, 답할 수 없는 질문의 처리, 도구와 인자 선택 등 실제로 영향을 받는 항목을 평가한다. 자연어 답변은 핵심 사실과 근거를 평가하고 구체적인 의미 판정 기준을 기록한다.
- 같은 평가 데이터와 판정 기준으로 이전 버전과 비교한다. 평가 데이터, 모델, 프롬프트, 검색 설정, 소스와 환경의 버전을 기록하고 달라진 조건을 설명한다. 이전 버전에 해당 기능이 없는 경우에는 비교 대상이 없는 이유를 남기고 현재 기능의 요구사항을 검증한다.
- 비결정적인 항목의 반복 횟수, 집계 방식, 통과 기준은 사전 계획에서 정한다. 결과를 본 뒤 통과한 실행만 선택하거나 기준을 낮추지 않는다. 중요한 기준 변경은 D06~D07을 따른다.
- 평가 결과와 근거를 검사 계획의 기준 버전에 연결한다. 필요한 평가나 환경이 없으면 D04~D05에 따라 해당 기능을 사용 가능으로 판정하지 않는다. 연동과 도구 실행 정책에 영향을 주는 경우 D30과 D35도 적용한다.

## 성능·장시간 검사 — 확정 규칙 D37

- reviewer는 변경 영향과 위험, 성능 요구사항을 기준으로 검사의 필수 여부, 대상, 부하, 실행 시간을 정한다. D29의 사전 계획에 선정·생략 이유와 검증할 범위를 기록한다.
- 이미 정해진 응답 시간, 처리량, 메모리,GPU 자원 등 필수 요구사항과 검사는 유지한다. 수치 완화와 필수 검사의 삭제·선택 전환은 D06~D07을 따른다.
- 검사를 선정하면 소스와 환경, 입력 규모, 동시 요청 수, 측정 지표, 실행 시간, 통과 기준을 연결한다. 이전 버전과 비교할 때 달라진 조건을 기록한다. 실제 값과 명령은 프로젝트별로 정한다.
- 필요한 범위의 검사와 유효한 기존 근거를 재사용한다. 새 변경·실패·미해결 우려가 없으면 통과한 전체 부하·장시간 검사를 반복하지 않는다. 새로운 영향에 필요한 검증은 해당 범위에 맞춰 진행한다.
- 필수로 정한 검사의 미실행이나 환경 미준비는 D04~D05의 판정을 따른다. 실행에 필요한 시간과 자원은 계획에서 기록하며 검사 선정이 사용량 정책과 실행 권한을 바꾸지 않는다.

## 핵심 테스트의 검증력 확인 — 확정 규칙 D38

- reviewer는 요구사항과 변경 위험을 기준으로 검사할 핵심 로직을 선정한다. test_agent는 D29의 계획에서 대상 로직·주입할 오류·실패해야 하는 검사와 기대 근거를 연결한다. 모든 수정에 전체 오류 주입 검사를 일괄 적용하지 않는다.
- 확인된 정상 코드와 격리된 복사본을 비교한다. 복사본에 권한 검사 누락, 중복 방지 제거, 잘못된 상태 전이 등 목표 동작을 잘못 바꾸는 오류를 넣고 해당 검사가 실패하는지 확인한다. 검증 대상이 아닌 문법·import 오류나 환경 실패를 검증 성공으로 세지 않는다.
- 정상 결과, 오류 내용, 목표 검사의 실패 결과와 소스·환경 근거를 기록한다. 목표 오류를 잡지 못하면 필요한 검증을 보완하고 독립 reviewer가 확인한다. 수정 반복과 시간 상한은 D17~D18, 기준 변경 권한은 D06~D07을 따른다.
- 오류를 넣은 복사본은 검사용이며 원본·운영 코드·배포 산출물에 반영하지 않는다. 확인한 안전한 코드와 검증 결과를 최종 검토에 연결하고 필요한 환경이 없으면 검사의 실제 상태와 남은 항목을 기록한다.
