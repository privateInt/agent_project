## 작은 단위로 끝내기

- 작업마다 목표, 변경 범위, 제외 범위, 완료 조건을 먼저 고정한다.
- 한 단위의 코드·관련 검사·필요한 실제 인수·기록을 마친 뒤 다음 단위로 진행한다.
- 이미 허용한 일반 코드 수정·조회·격리 검사·로컬 Git 작업에 반복 확인을 요구하지 않는다.
- 새로운 권한·목적지·비용·원본 삭제/교체가 필요하면 현재 승인 범위를 대조하고 구체적인 영향과 필요한 입력을 제시한다.
- 긴 작업은 마지막으로 확인된 소스/커밋, 결과, 다음 명령, 필요한 입력을 기록한다. 추측으로 완료 처리하지 않는다.

## 원본과 운영 자산 보존

- 사용자 미커밋 변경과 실제 Git/remote/branch를 확인하고 작업을 격리한다.
- 기존 DB, 인증, 설정, 키, 운영 데이터, 버전/요청 ID, 실패 이력, receipt를 보존한다.
- 운영 init/migrate·이미 성공한 생성/발행·실패한 terminal 실행을 이유 없이 반복하지 않는다.
- 공유 기능은 담당 플랫폼의 공식 API/계약을 사용한다. 타 플랫폼 저장소/DB를 직접 수정하는 일을 일반 연동으로 처리하지 않는다.
- 비밀 값·개인 원문을 로그/문서/Git/검사 산출물에 넣지 않는다.
- 임시 산출물 정리는 현재 단계의 입력 목록과 대조한다. 인증 저장소·운영 설정·원본·아직 참조하는 근거는 정리 대상에서 제외한다.

## 검사와 완료 근거

- 변경 동작을 검증하는 기존 검사를 우선 사용하고 필요한 회귀 검사를 보완한다.
- 통과한 전체 검사를 새 변경·실패·미해결 우려 없이 반복하지 않는다.
- PASS, FAIL, SKIP, BLOCKED와 기존 실패를 구분한다. 새 회귀 0개를 전체 제품 인수 완료로 해석하지 않는다.
- 기존 실패는 같은 소스/환경의 재현 근거와 구체 검사 이름을 남긴다. 광범위한 오류 무시나 임의의 예외 목록으로 새 실패를 통과시키지 않는다.
- 구현 검사, 격리 fixture, 실제 서버/브라우저 인수, 의미/품질 평가는 각각의 근거와 한계를 기록한다.
- 기대값·검증 gate·인증·소유권 검사를 약화해서 통과시키지 않는다.
- 테스트가 모두 통과해도 검사하지 않은 제품 요구는 완료로 표시하지 않는다.
- 환경 부족으로 실행하지 못한 필수 검사는 프로젝트 완료 조건에 따라 미완료로 처리한다.

상세 검사 기준과 사전 계획 절차는 [TESTING.md](TESTING.md)에 둔다. D28~D38의 본문을 이 문서에 중복 보관하지 않는다.

## 에이전트 협업

- 각 작업에 구현 담당, 변경할 파일/계약, 필요한 검증, 통합 담당을 정한다.
- 같은 파일의 동시 수정은 피한다. 공유 계약을 바꾸기 전에 영향을 받는 역할과 대조한다.
- 역할 수와 동시 실행 수를 따로 정한다. 독립적인 범위에만 병렬 작업을 배정한다.
- 구현자와 검증/검토 담당의 결과를 구분한다. 검토 결과는 구체 경로·동작·근거로 보고한다.
- 대화 기억만으로 재개하지 않는다. 확정 결정과 현재 상태를 저장소/작업 기록에 남긴다.

## 보고와 다음 단계

- 결과, 변경 이유, 확인한 검사, 남은 한계를 먼저 설명한다.
- 실패 시 실행 계정/환경/단계/검사 이름과 재현 가능한 작은 근거를 남긴다. 다른 권한이나 경로로 임의 우회하지 않는다.
- 검사 성공, 로컬 적용, GitHub 반영, 운영 배포를 구분해 보고한다.
- 현재 사용자 지시에 따라 본격적인 Codex 기능 개발 전에 사용자에게 먼저 알리고 공통 규칙·에이전트 구성·프로젝트별 템플릿 준비를 마친다.

## 프로젝트 문서 관리 — 확정 규칙 D19

이 절은 모든 프로젝트에 적용하는 문서 관리 규칙이다. `history_docs/`는 보관용 디렉터리이며 루트 README와 구분한다. 실제 프로젝트의 문서 이동은 현재 참조와 내용을 확인한 뒤 수행한다.

| 위치 | 책임 | 관리 기준 |
|---|---|---|
| 루트 README.md | 프로젝트 소개와 사용 시작 안내 | 목적·주요 기능·시작 방법·개발 문서 진입 링크를 관리한다. 상세 계약이나 일지를 반복해서 담지 않는다. |
| docs/ | 현재 개발·검증·운영·인수인계에 필요한 문서 | 현재 설계·API/DB 계약·테스트/인수 기준·운영 절차·작업 상태·유효한 결정·미해결 문제를 관리한다. |
| history_docs/ | 현재 개발에 사용하지 않는 과거 일지 | 완료된 실행 경과·과거 세션 기록 등 참고용 이력을 보관한다. 보관을 삭제로 해석하지 않는다. |

- 문서의 오래된 날짜만으로 보관하지 않는다. 현재 구현·계약·판정·복구·추적에 필요한 내용이 있으면 개발 문서로 유지한다.
- 개발에 쓰이는 부분과 과거 일지가 섞인 문서는 유효한 결정·계약·미해결 작업을 해당 최신 docs 문서에 반영한 뒤 일지를 보관한다. 과거 본문을 현재 상태에 맞춰 다시 쓰지 않는다.
- docs 하위 디렉터리는 프로젝트의 기능·플랫폼·주제에 맞게 에이전트가 자유롭게 만들고 정리할 수 있다. 새 폴더를 만들기 전에 기존 구조를 확인하고, 같은 주제의 폴더·동일 내용을 담은 문서를 중복 생성하지 않는다.
- 현재 설명과 규칙은 주제별 기준 문서 한 곳에서 관리하고, README·목록·인수인계 등 다른 문서에서는 링크로 참조한다. 프로젝트별 세부 규칙도 공통 규칙을 복사하지 않고 참조한다.
- 문서를 보관할 때 README·docs·코드·스크립트·테스트에서 사용하는 경로와 링크를 확인하고 이동된 위치 또는 최신 기준 문서로 갱신한다. 기계가 읽는 보고서·manifest·고정 경로의 입력은 호환성과 기존 검증 근거를 확인한 뒤 이동한다.
- AGENTS.md처럼 도구가 정해진 위치에서 읽는 규칙·설정 파일은 필요한 위치에 유지하고 docs의 상세 문서를 참조한다.
- history_docs로 옮겼다는 이유로 현재 요구사항·중요한 실패·검증 기준을 해제하지 않는다. 중요한 테스트 기준 변경에는 D06의 사용자 결정 규칙을 적용한다.
- 담당 에이전트는 변경된 기능의 최신 개발 문서와 진입 링크를 함께 갱신한다. 문서 정리의 변경 이유와 남은 참조 문제는 작업 기록에 남긴다.

## 모든 프로젝트에 포함하는 배포 방식 — D39

- 각 저장소는 공통 규칙·테스트 기준·구성표·결정 기록·템플릿을 함께 포함한다. 저장소 하나만 받아도 기준을 읽을 수 있어야 한다.
- 공통 내용은 같은 버전의 동일한 본문으로 배포한다. 저장소별로 독립적인 공통 정책을 만들지 않는다. 변경 시 영향받는 프로젝트에 같은 배포판을 반영하고 적용 여부를 기록한다.
- 배포판의 파일 목록과 SHA-256은 `release.json`에 둔다. 해시는 일치 여부를 확인하는 근거이며 파일 수정 권한이나 테스트 기준 변경을 막는 보안 장치는 아니다.
- 프로젝트별 책임·경로·검사 명령·현재 상태·예외는 `../project.md`와 기존 기준 문서에 둔다. 공통 정책을 프로젝트 문서에 다시 복사하지 않는다.
- 일부 저장소만 갱신됐으면 적용 대기 상태를 기록한다. 혼합 버전을 모두 적용 완료로 보고하지 않는다.

## 전달 방식 — D40

문서 진입점과 GitHub 반영 상태를 알려준다. 사용자가 요청하지 않은 다운로드 링크는 제공하지 않는다. 인증이나 환경 부족으로 반영하지 못했다면 준비 완료와 게시 완료를 구분한다.
