## 최초 점검: 판정과 범위

이하 과거 단계의 미확인·수정 계획은 당시 기록이다. 현재의 다음 작업은 [로드맵](../roadmap.md)이며 OCR 재실행을 필수로 두지 않는다.

최초 점검에 제공된 `정리한-결과 (1).json`, `정리한-결과 (1).md`를 원본 `AI_Engineer_sample.pdf`와 대조했다. **그림 내부 글자 인식과 복합 문서의 표·중복 없는 읽기 순서, 두 품질 검사는 모두 미통과다.** 구현 경로가 실행되는 것과 인식 품질을 구분한다. 이때는 제한 개선 또는 허용 범위를 먼저 정하려 했고, 이후 사용자는 부분 내용 보존을 우선하며 다음 단계로 진행하기로 했다. Knowledge는 미착수다.

이 검사는 제공 결과의 읽기 전용 분석이다. 원본 PDF 3–6페이지를 렌더링해 그림·표·본문 배치를 확인하고 JSON 구조 및 Markdown 변환을 검사했다. 서버 접속, 새 GPU 추론, Docker 빌드, DB/삭제 검사는 실행하지 않았다. 문서 한 개의 확인 결과이며 전체 문서군의 정확도 평가가 아니다. 페이지 번호는 인쇄된 번호가 아닌 **PDF의 물리 페이지**다.

## 검사 1: 그림 내부 OCR과 Markdown

| 페이지 | 페이지 OCR 상태 | 그림 추가 요청 | 최종 상태 |
|---|---|---|---|
| 1 | partial | v1·v2·v3 세 영역 실행 | 세 영역 모두 `visual_text_unread`, 결과 블록 0 |
| 3 | partial | v4 한 영역 실행 | `visual_text_unread`, 결과 블록 0 |
| 4·5·6 | completed | 추가 그림 요청 없음 | 표·본문 품질은 아래 별도 판정 |
| 2·7·8·9 | OCR 미선택 | 없음 | native parsing 결과 |

3페이지 원본에는 Raw cowhide, Trimming, Pre-soaking, Washing I, Main soaking 등의 글자가 있는 공정 흐름도가 있다. v4의 실제 crop 응답은 빈 `Diagram`과 `Figure 1. The system boundaries`라는 그림 제목만 반환했다. 최종 b71은 글자가 빈 image 블록이며 `recognition_status=unread`다. 내부 공정명과 흐름은 결과 본문에 들어오지 않았다.

추가 요청 자체가 빠진 것은 아니다. 네 영역 모두 응답이 기록돼 있고, 이번 기록에서 시간·개수 제한 초과나 OOM을 실패 원인으로 확인하지 못했다. 현재 모델/요청 방식이 이 샘플의 도표를 전사하지 못한 결과다. 모델이 모든 그림에서 인식할 수 없다고 일반화하지 않는다.

수정 전 `enrich_visual_regions()`는 crop 응답에 미인식 그림이 하나라도 남으면 영역 전체를 실패로 처리한다. 따라서 v3의 `Register now!`와 v4의 그림 제목도 최종 본문에 합쳐지지 않고 raw 응답에만 남았다. 부분 글자 보존은 보완할 수 있으나, 제목만 넣는 것으로 흐름도 내부 OCR 성공을 선언해서는 안 된다.

당시 `src/platform/data/console/data_results.py`의 `markdown_document()`로 첨부 JSON을 변환한 문자열은 첨부 Markdown과 **완전히 일치**했다. Markdown 저장 과정의 별도 누락이 아니라 최종 JSON에 읽힌 그림 내용이 없는 문제다. 성공한 그림 글자가 Markdown에 들어가는 경로의 과거 합성 검사는 있으나, 이번 실제 결과에는 성공 영역이 없어 실제 성공 사례를 검증할 수 없다.

## 검사 2: 표·읽기 순서·중복

이번 결과는 표 후보 다섯 묶음 중 OCR 네 개, 파서 한 개를 선택했고 모두 `needs_review`다.

| 비교 ID / 최종 블록 | 페이지 | 선택 | 선택 후보 구조 검사 | 원본 대조 |
|---|---:|---|---|---|
| t1 / b87 | 4 | OCR | 28행 × 10열, `missing_cells` | 공정명 누락·열 위치 오류 확인 |
| t2 / b93 | 5 | OCR | 50행 × 10열, `missing_cells` | 복잡한 연속 표; 전체 셀 정답 판정은 미실시 |
| t3 / b106 | 6 | parser | 3행 × 3열, `missing_cells` | 일반 문단을 표로 오인, b105와 중복 |
| t4 / b99 | 6 | OCR | 15행 × 10열, `missing_cells` | 전체 셀 정답 판정은 미실시 |
| t5 / b103 | 6 | OCR | 26행 × 4열, 구조 검사 통과 | Table 2 일부 값 원본 일치 확인 |

행·열 수와 `valid`는 후보 구조 지표이며 정확도 점수가 아니다. parser 후보의 구조 검사가 통과했다고 원본보다 정확하다는 뜻도 아니다. 특히 무테 표의 추정 후보는 다른 행·열 구조를 만들 수 있다.

확인한 결함:

1. 4페이지 원본 Table 1의 오른쪽에 있는 **14. Sammying**, **15. Shaving** 공정 구분이 t1의 최종 셀에서 빠졌다. 재료명 `Cowhide, sammying`이 있는 것은 공정명·공정 번호의 보존을 뜻하지 않는다.
2. t1의 열 제목은 왼쪽/오른쪽 각각 `No. / Process / Inputs and Outputs / Amount / Unit`이다. `Chromium VI`는 원본 오른쪽의 투입물인데 JSON에서는 0부터 센 column 4, 왼쪽 Unit 열에 들어갔다. `47.44`는 column 6, 오른쪽 Process에, `Kg`는 column 7, 오른쪽 Inputs and Outputs에 들어갔다. 원본의 항목·수량·단위 관계가 깨진 사례다. Markdown 표시만 바꾸어 복구할 수 없다.
3. 6페이지 b106의 세 셀은 기후변화 본문의 연속 문장이다. 공백을 제거해 대조하면 모두 바로 앞 b105의 OCR 본문에 포함된다. 원본에서도 일반 문단이며 표가 아니다. parser fallback 후보가 다시 삽입돼 중복 본문과 가짜 표가 생겼다.

긍정적으로 확인한 범위도 있다. t5/Table 2에서 Pre-soaking `6.30E+00`, Tanning `5.00E+01`, Setting out `2.86E+02`, Terrestrial ecotoxicity `1.03E-17`은 원본과 일치했다. 이는 일부 값의 대조 결과이며 표 전체의 정확도 점수는 아니다.

읽기 순서는 최종 267블록의 `id=b1…b267`, `order=0…266`과 페이지 순서가 일관됐다. OCR 페이지는 응답 HTML의 순서, native 페이지는 기하학적 추정 순서를 사용한다. 추가 그림의 성공 블록은 원래 그림 위치에 삽입하는 구현이다. 그러나 번호 일관성은 실제 읽기 순서의 정답 검증이 아니다. 중복 b106과 그림 내부 누락이 있으므로 **중복·누락 없는 의미 순서 검사는 미통과**다. 그림 화살표 관계를 해석하는 기능도 검증하지 않았다.

## 최초 점검 당시의 검증 목표

1. **그림 전사**: 같은 원본의 3페이지 영역에서 내부 공정명·숫자를 읽는 실제 응답을 확보한다. 같은 빈 그림 응답을 반복 제출하는 것으로 해결 처리하지 않는다. 부분 응답 보존을 수정한다면 미인식 그림 표시를 유지하고, 성공 글자만 원래 위치에 한 번 넣어 JSON/Markdown을 함께 확인한다.
2. **표와 중복**: t1의 누락·열 이동을 원본 기준으로 바로잡는 방법을 검증한다. t3/b106처럼 native 문단을 표로 오인한 fallback이 OCR 본문과 중복 삽입되지 않도록 재현 검사한다. 사용자가 정한 OCR 우선 정책을 임의로 parser 우선으로 뒤집지 않는다.
3. **시간**: 동일 원본·모델·처리 방식에서 품질과 요청 시간을 함께 비교한다. 최적화가 누락을 늘리지 않아야 한다. 실제 전체 대기는 Operation 시각·Job 로그가 있을 때 따로 평가한다.

당시에는 두 검사의 개선 또는 입력 허용 범위를 먼저 확정하려 했다. 이후의 결정은 읽힌 블록과 불확실 상태를 구분해 Knowledge에서 활용하는 것이며, 기존 실험 전체 PASS를 시작 조건으로 두지 않는다. `needs_ocr` 자료를 자동으로 완전한 RAG 입력으로 취급하지 않는다. 이번 정리는 원본·결과를 수정하거나 새 작업을 제출하지 않았다. 첨부 결과 전체·렌더링 이미지·실행 로그를 프로젝트 안에 중복 저장하지 않고 이 문서에 근거와 판정을 남겼다.

## 같은 날 추가 점검: 실제 응답 재생과 정답 대조

사용자가 세션 이동보다 품질 검사를 더 진행하겠다고 요청해 검사를 확대했다. 기존 실패를 통과로 바꾸지 않았으며, 서비스 수정·새 서버 추론을 수행하지 않았다. 아래 근거는 앞선 표본 대조를 확장한 결과다.

### 입력부터 출력까지 재현

당시 원본 PDF를 해당 버전 파서로 다시 읽고 페이지 응답 5개와 그림 crop 응답 4개, 총 9개를 재생했다. **9개 전송 PNG 해시가 모두 실제 기록과 일치**했으며 최종 JSON은 계측 시간 필드를 제외하면 첨부 결과와 완전히 일치했다. HTTP 호출은 차단했다. 로컬 재생 시간은 실제 GPU 지연과 비교하지 않는다.

OCR 단계 직후에는 266블록, 표 비교/병합 이후에는 267블록이었다. 6페이지의 문제 문장은 native 추출에도 한 번, OCR 직후에도 한 번 있었고 최종 결과에서 두 번이 됐다. 추가된 b106은 native가 일반 문단을 표로 오인한 후보다. 그 영역이 큰 OCR 문단 b105 안에 들어가 있는데, 수정 전 중복 제거는 반대로 표가 문단을 완전히 감싸는 경우만 처리한다. 이 방향 차이 때문에 문단과 가짜 표가 함께 남았다.

모델 응답 HTML을 직접 블록으로 변환한 네 OCR 표의 셀은 최종 b87·b93·b99·b103과 모두 일치했다. 4페이지 `Sammying`, `Shaving` 공정 라벨은 raw 표에도 없고, `Chromium VI / 47.44 / Kg`가 잘못된 열에 배치되는 HTML 행/병합 구조도 이미 raw 응답에 있다. 후처리가 정상 표를 틀린 표로 바꾼 사례로 해석하지 않는다.

Table 2는 셀 단위 완전 대조지만 4페이지의 2/11은 **선택한 관계의 점검 결과**다. 문서 전체 정확도 18%로 해석하지 않는다. 공백과 NFC만 정규화하고 숫자 부호·지수·문장부호·대소문자를 보존했다. 원본의 화학식 하첨자는 정답의 일반 텍스트 숫자로 전사했다. 그림 화살표 관계나 문서 전체 CER는 이 검사 범위가 아니다.

첫 보고의 공정명 `15. Shavings`는 원본을 다시 확인해 **15. Shaving**으로 정정했다. 해당 번호/공정명이 결과에서 누락됐다는 판정은 같다.

### 그림 영역 보조 실험

실제 v4와 같은 1600×671 이미지에서 글자들이 사람 눈으로 식별되며 crop 좌표가 그림을 잘라 버린 문제는 확인되지 않았다. 로컬 Tesseract 5.3.4/eng로 같은 이미지를 읽었을 때 psm 6은 그림 제목만, psm 11은 제목과 `Wetting back`만 읽었다. 다른 엔진으로 바꾸기만 하면 해결된다고 판단하지 않는다.

진단 목적으로 내부 글자 영역 세 곳을 **수동 지정**하여 psm 7로 읽으면 `Raw cowhide`, `Washing III`, `Neutralization` 세 문구는 모두 인식됐다. 이는 원본 내부 글자를 읽을 가능성과 세부 영역 분리 실험의 근거다. 자동 영역 탐지·현재 Surya 배포·다른 그림에서의 성공을 검증한 것은 아니며 서비스에 Tesseract를 추가하지 않았다. crop의 내부 미인식+제목 응답에서 일부 글자까지 버리는 후처리와 내부 글자를 전사하지 못하는 모델 응답은 별개로 고쳐야 한다.

### 재실행 방법

검사 도구는 `src/platform/data/tests/audit_document_quality.py`, 도구 회귀는 `test_document_quality_audit.py`다. 도구 회귀 **12개 통과**를 확인했다. 열 이동·지수 부호 변경·병합 오류·다른 영역의 같은 단어·raw 응답만 존재하는 경우·중복 문단·다른 원본을 거절하는 검사가 포함된다. 이것이 실제 샘플의 품질 PASS를 의미하지 않는다.

서비스 이미지를 다시 빌드하지 않고, 원본 PDF와 내려받은 JSON/Markdown의 실제 경로를 지정한다. 아래 `/실제/경로`는 사용자가 보관한 경로로 바꾼다.

```bash
cd ~/workspace/agent_project/data_platform
python -B tests/test_document_quality_audit.py -v
python -B tests/audit_document_quality.py \
  --source '/실제/경로/AI_Engineer_sample.pdf' \
  --canonical '/실제/경로/정리한-결과 (1).json' \
  --markdown '/실제/경로/정리한-결과 (1).md'
```

기본 검사는 Python 표준 라이브러리로 실행하며 파일을 읽고 판정 JSON을 stdout에 출력한다. 새 작업·모델 배포·파일 수정·Docker 컨테이너 생성은 없다. 종료 코드 0은 이 고정 검사 항목 통과, **1은 품질 실패**, 2는 입력/실행 조건 오류다. 여기서 기록한 미통과 첨부 결과는 1로 종료하는 것이 맞다. 새 결과는 그 결과의 실제 판정을 따른다. `set -e` 안에 넣으면 품질 실패에서 멈춘다.

동일 OCR 응답을 전체 파이프라인에서 재생하려면 마지막 명령에 `--replay`를 붙인다. 이때 프로젝트 파서의 의존성 `src/platform/data/jobs/refinement/parse/requirements.txt`가 필요하다. 이번 로컬 환경의 pdfplumber 0.11.8, Pillow 12.3.0, pypdfium2 5.3.0, lxml 6.1.1은 해당 파일과 일치했다. 재생은 서버 접속을 차단하고 결과의 모델 식별자를 증거로만 사용한다. 버전/코드 변경으로 전송 이미지나 결과가 달라지면 일치를 실패로 표시한다. 그것만으로 새 결과의 품질이 나빠졌다고 단정하지 않고 개별 정답 검사를 함께 본다.

이 정답은 현재 하나의 합쳐진 10열 Table 1 표현을 기준으로 한다. 앞으로 좌우 표를 분리하는 계약으로 바꾼다면, 출력에 맞춰 정답을 자동 생성하지 말고 원본의 논리적 열 관계를 보존하도록 검사기를 확장해야 한다.

### 추가 점검 당시의 수정 순서

1. **native 표 fallback 중복 삽입**: 먼저 로컬에서 고칠 수 있다. 원본 후보는 증거에 남기되 OCR 본문에 이미 보존된 일반 문단을 표로 다시 삽입하지 않도록 한다. 실제 표나 다른 문단을 삭제하지 않는 회귀·Go canonical 계약 확인이 필요하다.
2. **crop 부분 글자 보존**: 읽힌 글자만 위치에 맞게 보존하고 남은 이미지의 unread 표시를 유지한다. 제목만 반환된 사례를 내부 그림 인식 성공으로 승격하지 않는다.
3. **복잡한 표·그림의 OCR 입력/응답 개선**: 좌우 표나 그림 내부 글자 영역을 분리하는 후보를 실제 배포로 비교한다. 새 GPU 추론이 필요한 단계다. 동일 원본·배포·품질 기준을 유지하고 시간도 함께 측정한다.

사용자 서버의 새 GPU 추론을 여기서 대신 실행하지는 못했으나, 이를 제외한 위 원본 대조·실제 응답 재생·검사기 검증은 완료했다. 이번에는 품질 검사와 재현 도구만 추가했으며 서비스 버그 수정은 아직 적용하지 않았다. Knowledge 단계는 계속 미착수다.

## 후속 구현: 중복 표 방지·crop 부분 글자 보존

위 표와 블록 번호는 수정 전 서버 결과의 기록이다. 이후 사용자의 계속 진행 요청으로 병합·보존 코드를 수정했다. **이 절의 결과는 저장 응답 재생이며 새 GPU 추론 결과가 아니다.** 원본 PDF와 기존 JSON/MD는 변경하지 않았다.

- native의 희소한 문장형 가짜 표가 같은 영역 OCR 본문에 순서대로 완전히 포함되면 중복 삽입을 막는다. 실제 표·다른 숫자·다른 순서·부분 일치·다른 위치·OCR 표가 있는 경우는 보존한다.
- crop에 읽힌 글자와 빈 그림이 함께 있으면 읽힌 블록을 최종 본문/Markdown에 넣는다. 원래 unread 위치와 partial/needs_ocr는 남긴다. 미인식 child에 재귀 요청하지 않는다.
- Go Job/API는 partial 영역의 원래 unread 위치, 읽힌 child 수/참조/좌표 및 페이지·품질 상태를 함께 검사한다. 화면/MD는 완료·부분 인식·미확인을 나눠 센다.

|---|---|---|
| 페이지+crop 입력 | 5+4개 | 9개 PNG 해시 모두 동일, 네트워크 요청 0 |
| 최종 블록 | 267 | 269: 가짜 표 1개 제외, 읽힌 crop 블록 3개 추가 |

| crop 상태 | failed 4개 | partial 3개, failed 1개; 완료 0개 |
| 원래 미인식 그림 | 4개 | 동일 위치 4개와 needs_ocr 유지 |
| p3 내부 글자 | 0/24 | 0/24 — 그림 제목 보존만 확인 |

제외한 가짜 표와 추가한 crop 세 블록 외의 본문·표 내용은 동일하다. 재번호한 id/order/비교 ID를 제외해 대조했다. 기존 native 후보·입력 PDF·기존 결과의 해시도 동일하다. 보존된 `1`은 모델의 Page-Header 응답이며 원본 내부 글자를 새로 알아냈다는 근거가 아니다. OCR 텍스트를 수작업으로 교정하지 않았다.

관련 Python 108개(기본 파서 23, 좌표 5, 표 25, OCR 35, 출력/UI 8, 품질 검사기 12), Go canonical/runtime 최상위 15개가 통과했다. partial의 거짓 완료·원래 그림 누락/위치 변경·개수 불일치·잘못된 child 참조를 거절하는 회귀를 포함한다. 기존 267블록과 새 269블록 JSON 모두 실제 Go 검증기를 통과했고 정제 API/Job을 컴파일했다. 서버 Docker·GPU는 이 환경에서 실행하지 않았다.

당시 적용 패키지는 `data-platform-refinement-preservation-20260917.tar.gz`였다. 현재 소스에는 수정이 포함되어 있으므로 이 과거 패키지를 다시 적용하지 않는다. `apply.py`는 모든 변경 파일의 이전 해시를 확인한 뒤 소스/문서를 갱신하고, 별도 `activate.sh`는 테스트·이미지 빌드 후 정제 API → Job 태그 → 화면 순서로 활성화한다. 원본·결과·DB·모델 배포를 변경하거나 정제 요청을 자동 제출하지 않는다. 임시 테스트 컨테이너는 `--rm`으로 정리한다. 배포 단계가 실패하면 새 정리를 시작하지 말고 해당 오류를 먼저 확인한다.

당시 적용 후 새 정리 결과를 확인하도록 안내했고, 아래 서버 결과(3)에서 반영을 확인했다. 이후 재검증을 의도할 때만 같은 원본을 새로 정리한다. 기존 결과를 다시 다운로드하는 것만으로 본문 보존 수정이 적용되지는 않는다. `audit_document_quality.py --replay`는 현재 코드와 입력 JSON의 동일성 검사이므로 수정 전 JSON을 수정 후 코드로 재생하면 의도한 차이 때문에 불일치한다. 새 결과에서 재현성을 확인한다. 새 GPU 응답은 달라질 수 있어 269블록을 서버 통과 조건으로 고정하지 않는다.

복합 표의 열/공정 오류와 흐름도 내부 글자 누락은 남아 있다. 다음 품질 작업은 같은 원본·배포·정답 기준으로 OCR 입력/응답 전략을 개선하고 실제 시간과 정확도를 함께 확인하는 것이다. Knowledge는 아직 미착수다.

## 서버 후속 결과(3) 확인과 페이지·그림 중복 수정

사용자가 보존 패치 적용 후 `정리한-결과(3).json/.md`를 제공했다. 원본 ID/해시와 OCR 모델 identity는 이전과 같고 Job image는 `sha256:2d7961ac87068629c815790bb9d0ff07d729dfa1c6bb9af289c35dd6cc8499c8`로 바뀌었다. JSON SHA-256은 `1882c65aafa125fe60971dc696cbac4e8578b487b905459a6ea440e5ce82680b`, Markdown은 `55f6335af9a1347bafb5318486c47c9a260c7324d327a2f1f9e825ae43986a21`다.

이 서버 결과는 앞선 로컬 재생의 최종 269블록·quality·표 비교와 일치했다. 가짜 표 중복 제거와 partial 세 영역의 글자 보존이 실제 새 결과에 반영됐다. Markdown도 최종 JSON 변환과 일치한다. Table 2 85/85를 유지하지만 흐름도 라벨 0/24·복합 표 관계 2/11·공정명 0/2가 남아 있다. 전체 시간 180.005853초, OCR 178.620712초, 그림 추가 단계 2.286341초로 속도 개선을 확인하지 못했다.

추가로 p1 b14(crop v3)와 b15(페이지)의 `Register now!`가 같은 영역에 중복됐다. 이전 검사는 본문/표 중복만 검사해 이 결함을 놓쳤다. 별도 `no_overlapping_visual_text_duplicate` 검사를 추가해 첨부 서버 결과에서 실패하는 것을 확인했다.

다음 수정은 같은 글자·위치의 일대일 페이지/crop 대응만 합친다. 실제 응답 9개 재생 시 269→268블록, 문구는 Markdown에 한 번만 나온다. 그 외 본문은 ID/order 재번호 외에 동일하고, native와 raw 응답·미인식 네 위치·partial 상태를 유지했다. 제외한 페이지 블록은 보조 기록에 보존한다. 기존 269블록/수정 후 268블록 모두 Go canonical 검증을 통과했다. 관련 Python 114개(파서 23·OCR 37·좌표 5·표 25·감사 13·영역 실험 11)를 통과했다. 이 시점에는 서버 반영을 확인하지 못했고, 다음 절의 서버 로그에서 Job 활성화를 확인했다. 새 전체 문서 품질 검증은 보류다.

동시에 [영역별 OCR 실험](testing-ocr-quality.md#region-experiments)을 준비했다. 공정명 24개 원본 조각을 모은 그림과 Table 1 좌/우 이미지를 별도 정제해 같은 배포에서 전사/행열 보존을 측정한다. 실험 영역은 이 샘플에 지정한 위치이며 자동 탐지 성능이 아니다. 입력에 정답 글자를 써 넣지 않고 원본 픽셀만 사용한다. 결과를 원래 canonical에 자동 병합하지 않는다. 이 준비 시점에는 새 GPU 결과가 없었고 이후 수동/자동 실험을 완료했다. 블록 수 268은 저장 응답 재생 결과이며 새로운 추론의 고정 통과 조건이 아니다.


## 영역 실험 서버 시작 로그와 권한 수정

사용자 첨부 `붙여넣은 텍스트 (1)(20260917-041031).txt`에서 영역 패치 18개 파일 적용, parser-tests 빌드, 새 정제 Job의 self-test·활성화를 확인했다. 검사 image는 `sha256:54a702f21965f92614e2869d530d95a31aa2337cb422f0f562d40b26bd6a0fac`, 정제 Job image는 `sha256:26b2de683033cb62ba7a42071e0b3d3845611feaf99dafdb1db24a5905d354e8`다. 이는 배포/빌드 근거이며 실제 문서 품질 통과 근거는 아니다.

실험은 최초 import에서 `/app/tests/live_collection_smoke.py`를 읽지 못해 PermissionError로 종료됐다. 이 시점에는 API 조회·업로드·정제 요청이 발생하지 않았다. COPY 이후 파일/디렉터리를 일반 사용자가 읽고 탐색할 수 있게 만드는 단계가 없었고, root 빌드 검사에서는 해당 문제가 드러나지 않았다.

검사 stage에 `chmod -R a+rX /app/tests /app/jobs`와 `USER 65532:65532`를 추가했다. 관련 114개 검사와 실행 CLI의 `--help` import를 이제 non-root로 빌드 중 실행한다. 런타임을 root로 바꾸지 않으며 검사 컨테이너의 --rm/read-only/호스트 UID를 유지한다. 운영 파서·정제 Job 내용이나 영역 입력·채점 규칙은 바꾸지 않았다. 로컬의 권한 모드 검사와 같은 114개 검사·CLI import는 통과했으며, 이후 사용자 서버의 non-root 검사 이미지 빌드와 실험 실행도 확인했다. 현재 실행 조건은 [통합 실험 안내](testing-ocr-quality.md#region-experiments)를 따른다.

## 최종 자동 영역 실험과 사용자 마무리 결정

첨부 `붙여넣은 텍스트 (1)(20260917-072845).txt`는 문서/코드 패치 적용과 서버 검사 이미지 빌드, 9개 입력 완료 로그다. 최종 `report(1).json` SHA-256은 `db92f4385258e9a13a9adf7c5f8530b7ff840e03e0dae193923262305901b100`이며 실험 키는 `e5d805e6-11aa-4f0b-8f1f-5dc3a5f25240`다. complete=true, all_probes_passed=false, production_result_modified=false다.
