# 공통 설계 원칙

2026-09-28 사용자 확정 요구. **자동화와 적응성을 프로젝트 전체의 최우선 제품 설계 원칙으로 둔다.** Model·Data·Knowledge·Agent·Ops와 배포/운영 도구, 초기 설정 화면, 향후 기능에 공통으로 적용한다. 아래는 앞으로 설계·구현·검증할 기준이며 현재 모든 기능이 자동화됐다는 완료 선언은 아니다.

## 두 원칙의 의미

| 원칙 | 사용자 관점의 목표 | 개발 판단 기준 |
|---|---|---|
| 자동화 | 사용자가 직접 설정하고 연결하고 반복 조작하는 부분을 최소화한다. | 코드로 알아낼 수 있는 값은 자동으로 채우고, 같은 정보를 여러 곳에 입력하거나 설치/변경 때마다 수정하게 하지 않는다. |
| 적응성 | 다양한 사용자 환경에서 고정 주소·이름·경로에 의존하지 않고, 검색·발견·기능 확인을 통해 환경에 맞춰 간편하게 동작한다. | 환경이나 서비스 주소가 달라져도 공통 기능 코드는 유지하고, 해당 환경의 발견 방법으로 실제 대상을 찾아 연결한다. |

자동화는 스크립트 실행이나 반복 작업 예약에만 한정되지 않는다. 최초 설치의 필수 입력 수, 환경 변경 후 수동 수정량, 장애 이후 재설정량도 줄여야 한다. 적응성은 IP를 환경 변수나 설정 파일로 옮기는 것에서 끝나지 않는다. **설정 분리는 기반이고, 환경·대상 발견과 연결 정보 생성·갱신까지가 목표다.**

“어떠한 환경에서도 간편하게 사용”을 장기 제품 목표로 삼는다. 완료 판정은 지원 환경별 실제 검증 근거로 구분한다. 미지원 환경이나 조회 권한 부족은 이유와 필요한 최소 조치를 보여주며, 다른 환경의 값을 대신 넣어 정상으로 표시하지 않는다.

## 사용자에게 요구하는 설정을 줄이는 방법

1. 기존 설치 정보와 사용자가 이미 지정한 설정·접근 권한을 먼저 재사용한다. 재실행 시 계정·키·식별자를 새로 만들거나 같은 질문을 반복하지 않는다.
2. 실행 환경, 서비스 후보, 제공 기능, 연결 가능 여부와 자원 범위를 자동으로 조사한다. 설치용 시작점이나 접근 자격처럼 스스로 알 수 없는 값만 한 번 입력받는다.
3. 신원과 기능이 일치하는 대상이 하나로 결정되면 연결 정보와 환경 설정을 자동 생성한다. 후보가 여러 개면 사용자가 이해할 수 있는 이름·소속·기능과 함께 필요한 선택만 제공한다.
4. 선택 결과와 생성 근거를 보관하고 다음 실행에 재사용한다. 같은 리소스의 주소가 바뀌면 재발견·재검증하여 갱신한다. 전송 재시도는 기존 멱등/실행 계약을 따른다.
5. 기본 화면에는 사용 가능 여부와 해결할 항목을 보여준다. 상세 주소·라벨·고급 설정은 필요할 때 확인·재정의할 수 있게 한다. 자동으로 결정한 값도 확인 가능해야 한다.

명시적인 사용자 재정의는 자동 발견보다 우선하며 선택한 대상의 신원·호환성을 검증한다. 재정의는 예외 환경의 탈출구로 제공하고, 일반 사용자가 다수의 주소·job·경로를 채워야만 시작하는 흐름을 기본으로 삼지 않는다.

## 환경에 맞춰 대상을 발견하는 구조

공통 기능은 논리적 리소스와 API 계약을 사용한다. 환경별 adapter가 탐색·기능 확인·연결 정보 생성·변화 감지를 담당한다. 아래는 구현 방향이며 모두 현재 제공된 기능은 아니다.

| 대상 | 발견·적응 방향 | 공통 기능에 남길 정보 |
|---|---|---|
| 플랫폼·서비스 | 기존 배포 메타데이터, 서비스 DNS, 등록 목록, 소유 플랫폼의 공식 API에서 대상과 기능 조회 | 서비스/프로젝트 신원, API 버전·기능, 검증한 endpoint·인증 참조 |
| Docker Compose | 허용된 배포 관리 계층에서 project/service label·네트워크·실제 연결/마운트 정보 조회 | 논리 서비스·리소스 ID와 실제 배포 연결 |
| Kubernetes | 선택한 cluster/context 범위에서 Service/EndpointSlice·Pod·Node·라벨 등 발견, 변경 추적 | cluster·namespace·리소스 UID·소유 관계와 연결 정보 |
| CPU·메모리·GPU·지표 | collector가 제공하는 대상·지표·라벨·지원 기능을 확인하고 조회 조건 생성 | 노드/컨테이너/GPU 식별자, 단위·측정 의미·관측 시각·지원 여부 |
| 저장소·백업 후보 | 실제 마운트·파일시스템 또는 PVC/PV/StorageClass 관계, 용량·접근 조건 조회 | 논리 저장소 ID, 연결 관계, 측정 범위와 미확인 조건 |
| 모델·도구·연동 기능 | 소유 플랫폼의 배포 목록·capability/API 명세를 조회하고 호환 후보를 제시 | 고정한 모델/버전/공간·Tool/Connection ID와 기능 계약 |
| 접속 주소 | 내부 서비스 연결과 사용자가 접근하는 공개 주소를 구분하고, 배포에서 얻을 수 있는 주소를 활용 | 검증한 내부 endpoint와 외부 URL, 필요한 경우 최소 입력 |

컨테이너 재생성·Pod 이동·포트/마운트 변경·수집 대상 증감에 적응해야 한다. IP·현재 컨테이너 ID·단일 호스트 경로를 영구적인 리소스 신원으로 사용하지 않는다. 여러 cluster/namespace의 동명 리소스는 구분하고, 관측 출처와 범위를 유지한다.

탐색은 사용자가 선택하거나 기존 설정으로 확인된 환경과 허용된 접근 범위에서 수행한다. 설치된 kubeconfig와 Docker가 함께 존재한다는 사실만으로 사용할 환경을 임의 결정하지 않는다. 필요한 시작점/권한이 없거나 선택이 불분명할 때만 최소 정보를 요청한다. 전체 네트워크의 무차별 포트 탐색을 기본 발견 방식으로 삼지 않는다.

## 플랫폼 독립성과 기존 계약

자동 연결은 각 플랫폼의 소유권과 공식 API 경계를 유지한다. Ops 웹에 Docker socket이나 타 플랫폼 DB 접근을 추가하는 대신, 환경 조사는 배포/infra adapter가 맡고 Ops는 허용된 API와 관측 결과를 사용한다. Knowledge와 Data가 발견한 Model 기능도 Model API로 이용한다. Tool·Agent 자산과 실행 상태는 Agent에 유지한다.

같은 리소스의 주소 갱신에는 기존 논리적 신원·모델 버전·임베딩 공간·인증 참조를 유지한다. 새 모델·다른 인덱스·다른 저장소로 전환하는 정책은 소유 플랫폼의 명시된 계약에 따른다. 자동 발견 단계에서 데이터 삭제, 권한 완화, 다른 서비스 재시작 같은 업무 변경을 함께 수행하지 않는다. 기존에 허용된 일상적인 설정 재사용과 연결 복구는 반복 승인을 요구하지 않는다.

## 개발·인수 기준

새 기능과 수정 기능은 아래 질문에 답한다. 문서상 설정 가능 여부와 실제 자동 발견·변경 적응 완료를 별도로 기록한다.

| 검토 항목 | 확인할 결과 |
|---|---|
| 최초 사용 | 필요한 사용자 입력·수동 명령·설정 파일 수정 수와 각각 자동화할 수 없는 이유 |
| 다른 환경 | IP/포트·사용자명·프로젝트 경로·job/namespace/마운트명이 달라도 소스 수정 없이 지원 범위에서 동작 |
| 변경 적응 | 같은 서비스의 재생성·주소 변경·대상 추가/제거를 재발견하고 수동 재설정 없이 반영 |
| 재실행 | 기존 설정·키·리소스·데이터를 재사용하고 중복 생성하지 않음 |
| 후보 선택 | 대상 0개·1개·여러 개, 권한 부족·기능 미지원·일시 장애를 구분하고 최소 조치만 안내 |
| 범위와 신뢰성 | 동명 리소스·오래된 관측값을 구분하고 선택 근거·신원·버전·호환성 유지 |
| 운영 편의 | 결정된 설정과 원인을 확인할 수 있고, 고급 재정의와 변경 복구 방법 제공 |

지원 환경마다 최초 설정 입력 수, 환경 변경 후 수동 수정 수, 자동으로 발견·연결한 대상 범위와 미지원 항목을 기록한다. 환경 변경마다 코드나 여러 설정 파일을 고쳐야 한다면 자동화/적응성 목표의 미완료 항목으로 남긴다. 숫자 목표와 검증 환경은 해당 구현 단위에서 정하며, 문서만으로 달성한 것으로 처리하지 않는다.

## 작업을 단계별로 나누는 원칙

한 번에 너무 많은 작업을 진행하지 않는다. 각 단계는 목적·변경 범위·확인 방법·완료선·다음 단계가 구분돼야 한다. 실행 시간이 긴 작업은 구현, 격리 검증, 운영 적용, 결과 정리를 나눠 진행한다. 완료된 검증은 기존 근거를 재사용하며 새로운 변경이 영향을 준 범위만 다시 확인한다.

## 현재 상태를 관리하는 위치

설계 원칙에는 진행 로그를 누적하지 않는다. 구현/검증 상태는 [현재 상태](status.md), 우선순위는 [로드맵](roadmap.md), 환경별 근거는 각 날짜별 인수 문서에 둔다. 현재 지원 우선순위는 단일 노드 Docker이며 실제 재부팅과 Kubernetes 전환 보류 결정을 유지한다.
