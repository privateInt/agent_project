# n8n 운영 구성을 infra로 이전

**최신 서버 확인:** DB 권한 복구 후 PostgreSQL/n8n Healthy와 원래 키/볼륨 보존을 확인했다. 09:24 후속 로그에서 검사 이미지 a07.3 빌드와 격리 n8n CLI 검사 7개도 통과했다. [검증 근거·오류 이력](n8n-checks-fix-20260924.md)을 따른다. 아래 unhealthy·파일 접근 오류·미실행 서술은 이전 로그의 이력이다. 운영 기동과 통과한 검사를 반복하지 않는다.

2026-09-24. 사용자 결정: n8n은 infra 초기 기동에서 실행하고, Agent Platform에는 n8n을 활용하는 연동 코드만 둔다. Agent 빌드 `a07.1`, 계약 `agent.platform.v1/a07`, DB schema 5는 유지한다. 이번 패치는 배치·운영 절차 변경이며 A08 화면 작업이 아니다.

## 소유권과 파일 배치

| 위치 | 책임 |
|---|---|
| `src/infra/n8n` | 공식 n8n 이미지, 전용 PostgreSQL 16·앱 계정·schema, DB/데이터 볼륨·암호화 키, 기동·상태·진단 |
| `src/infra/docker-compose.yml` | n8n 서비스 구성을 include. 기존 infra 서비스와 함께 초기 기동 |
| `src/infra/ops/up.py` | 최초 설정·네트워크·외부 볼륨 준비, A07 설정 이전, 순서가 보장된 기동 |
| `src/platform/agent/n8n` | Agent 호출 워크플로 템플릿, 생성·WorkflowLink 등록 CLI, 격리된 연동 검사 |
| `src/platform/agent/service` / `runtime` | Tool·Agent 정의/버전/실행과 LangGraph 처리. n8n 설치·DB 관리 책임 없음 |

n8n 정의·자체 실행·자격은 n8n이 소유한다. Agent는 WorkflowLink 참조만 저장하며 n8n DB를 직접 읽지 않는다. n8n에 Agent/Model/Knowledge의 내부 DB·비밀·Docker/GPU 접근을 주지 않는다. Agent가 없어도 n8n은 기동하며, n8n이 없어도 Agent REST/MCP는 동작한다. n8n 기동은 비활성 예제 Flow를 등록하거나 실행하지 않는다. 기존에 활성화한 사용자 Flow는 n8n의 정상 재기동 동작을 따른다.

## 첨부 서버 로그 확인

`붙여넣은 텍스트 (1)(20260924-044402).txt`에서 다음을 확인했다.

- A07 패치 55개 적용, Go/Python 테스트 이미지 빌드, Agent 5개 서비스 Healthy.
- A03 기존 ToolCall `8e3b3160-8e29-49d8-96d2-e0540e67682e` 조회 PASS. request ID `b611f3d7-8d9f-4dc1-9110-04496f5278ea` 유지.
- PostgreSQL Foundation·Knowledge·OpenAPI·Tools DB, Agent·Knowledge·OpenAPI·Tools EndToEnd PASS. Agent 검사에 WorkflowLink API가 포함된다. 모델/지식 응답은 검사 대역이며 실제 사용자 답변 인수가 아니다.
- n8n 설정·사전 점검·이미지 다운로드 완료, 전용 PostgreSQL Healthy.
- `agent-flows-n8n-1`은 약 329초 후 unhealthy. `set -e`에 따라 후속 `n8n-checks`는 실행되지 않았다.

첨부에는 n8n 시작 로그와 healthcheck 출력이 없어 unhealthy의 직접 원인을 확정하지 않는다. infra 이전만으로 해결됐다고 표시하지 않는다. 새 기동기는 앱 계정의 실제 DB 접속/DDL을 확인하고, 실패하면 컨테이너 상태·healthcheck·최근 로그를 자동 출력한다. 알려진 DB 비밀번호·암호화 키·Bearer 값은 가린다.

## 기존 A07 서버에 적용

패치를 적용한 뒤 프로젝트 루트에서 실행한다. 다른 src/infra/Agent 서비스는 재빌드하거나 재시작할 필요가 없다.

```bash
cd ~/workspace/agent_project
python3 src/infra/ops/up.py --n8n-only
```

자동 처리 순서는 다음과 같다.

1. `src/platform/agent/n8n`의 기존 설정·DB 비밀번호·암호화 키를 `src/infra/n8n`으로 복사한다. 원본은 보존하며 키를 재생성하지 않는다.
2. 원래 `agent-flows_flows-db`, `agent-flows_flows-data` 볼륨과 컨테이너의 Compose 소유권·마운트·키 일치를 확인한다. 볼륨은 파일 복사 없이 그대로 연결한다. 누락/다른 소유자/불일치는 중단한다.
3. 이미지를 먼저 확보한다. 그다음 이전 n8n→DB 컨테이너의 자동 재시작을 해제하고 중지한다. 컨테이너·볼륨은 삭제하지 않는다.
4. 새 `infrastructure` 프로젝트에서 DB→DB 앱 접속 검사→n8n 순서로 실행한다. 준비 완료를 기다리고 실패하면 진단 출력을 남긴다.

기존 서버는 화면 없이 이 단계까지 확인할 수 있다. 성공 후 Agent 연동 검사는 다음과 같다. 실제 사용자 모델·지식 대신 격리 HTTP 대역과 일회성 SQLite를 사용한다.

```bash
cd ~/workspace/agent_project/agent_platform
docker compose -f n8n/tests/docker-compose.yml run --build --rm n8n-checks
```

오류를 다시 확인할 때는 프로젝트 루트에서 아래만 실행한다. 설정·키 원문이나 `docker inspect` 전체 출력 대신 이 결과를 전달한다.

```bash
python3 src/infra/n8n/ops/diagnose.py
```

## 처음 설치하는 환경

기존 infra 환경 설정은 종전대로 준비한다. 기본 실행은 n8n을 포함한 infra 전체이며, 아직 플랫폼을 기동하지 않아도 된다.

```bash
cd ~/workspace/agent_project
python3 src/infra/ops/up.py
```

최초 실행에서 전용 설정·세 키·명시적인 외부 볼륨 `ops-n8n-db`, `ops-n8n-data`와 공유 네트워크를 준비한다. 다음 실행에서는 재사용한다. 기존 데이터 볼륨만 있고 대응하는 설정·키가 없으면 초기화하지 않고 중단한다. 한번 준비한 볼륨이 없어져도 빈 DB를 재생성하지 않는다.

초기 준비 이후 일반적인 `cd infra && docker compose up -d --wait`에도 n8n이 포함된다. n8n 서비스만 관리할 때는 다음처럼 같은 `infrastructure` 프로젝트의 부분 구성을 사용한다.

```bash
cd ~/workspace/agent_project/src/infra/n8n
docker compose ps
docker compose stop n8n
# 다시 실행
python3 ../ops/up.py --n8n-only
```

다른 infra 서비스에 영향을 주지 않도록 부분 구성에서 `down`이나 `--remove-orphans`를 사용하지 않는다. n8n 볼륨은 external로 선언하여 Compose의 수명주기에서 분리했다.

## 설정·보존·복구

- UI 기본 포트 16200, LAN 바인딩 0.0.0.0. 실제 접근 주소는 `src/infra/n8n` 설정의 `N8N_PUBLIC_URL`로 지정한다. 기존 주소·포트도 그대로 가져온다.
- 기존 Compose 변수 `N8N_AGENT_NETWORK`는 호환성을 위해 유지하며 기본값은 `ops-infra`다. n8n이 Agent 기동에 의존한다는 의미는 아니다.
- A07 기본 프로젝트명/마운트가 기준이다. 사용자가 별도 프로젝트명·볼륨으로 운영했다면 자동으로 추정하거나 새 DB를 만들지 않고 중단한다.
- 새 기동기는 환경변수의 임시 Compose/N8N 덮어쓰기를 제거하고 저장된 설정을 기준으로 검사한다. 설정 변경은 해당 파일에 명시적으로 반영한다.
- 기존 `.env`, `.secrets`, DB/데이터 볼륨과 새 `.state.json`, `.storage.json`, `.handoff.json`을 운영 자산으로 보존한다. 비밀·운영 상태는 소스 패치나 전체 소스에 포함하지 않는다. 원본 A07 설정은 이전의 근거로 유지한다.
- 중지한 `agent-flows` 컨테이너는 롤백 조사용으로 남으며 자동 재시작은 `no`다. 기존·새 DB 컨테이너를 같은 볼륨으로 동시에 시작하면 안 된다. 앱 키나 DB 비밀번호를 임의 재생성하지 않는다.
- 기동 실패 후 같은 `up.py --n8n-only`를 다시 실행할 수 있다. 기존 리소스/키를 유지하며 볼륨 삭제, DB drop, 전체 infra 중지는 수행하지 않는다.
- DB는 기존 PostgreSQL 16과 고정 digest를 유지한다. n8n 2.40.5 공식 코드에서 16은 compatibility support, 17 이상은 supported range로 구분한다. 이번 배치 변경에서 기존 볼륨에 새 PostgreSQL major 이미지를 덮어씌우지 않는다.

## 검증과 보류

로컬에서는 실제 Docker Compose 2.39.4로 infra 전체(14개 서비스)와 n8n 부분 구성의 경로·설정 일치를 확인했다. 이전 코드의 키/설정 바이트 보존, 재실행, 볼륨 누락·다른 소유자·키 충돌·동시 실행 방지, 실패 순서를 검사한다. 구체적인 결과는 `src/platform/agent/tests/results/a07-infra-local-20260924.json`을 따른다.

로컬 Docker daemon이 없어 실제 컨테이너 소유권 이전은 서버에서 확인한다. n8n unhealthy 해소·서버 PostgreSQL 권한·준비 상태는 사용자 실행 결과로 확정한다. Agent/n8n 페이지·소유자 계정·편집/저장·실제 질문/출처 품질·재시작 후 실행 보존 확인은 사용자 요청대로 보류한다.
