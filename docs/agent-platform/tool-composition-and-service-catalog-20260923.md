# 자연어 검색 Tool 조합과 서비스별 API 관리

후속 반영: [A05 자연어 검색 구현·검증](knowledge-search-a05-20260923.md)을 추가했다. 아래는 구현 전 논의/요구 기록이며 범용 내부 API 자동완성·서비스 카탈로그는 후속으로 남긴다.

2026-09-23. 사용자는 자연어 질문을 받아 임베딩 API와 검색 API를 순서대로 호출하는 기능, 조합의 소유 위치, 서비스 단위 API 관리를 논의하고 이 방향을 기록하도록 요청했다. 이 문서는 합의한 개발 방향이며 **A05·서비스 카탈로그·범용 조합 기능의 구현 완료 기록이 아니다**.

## 사용자에게 제공할 기능

사용자는 질문을 입력하고 검색 결과를 받는다. 관리자는 검색할 지식과 연결을 선택한다. 중간 벡터를 만들거나 API 사이에서 복사하는 절차를 일반 사용자에게 요구하지 않는다. 현재 [시험 입력 준비 명령](tool-registration-20260923.md)은 A04의 개별 API 등록·실행을 확인하기 위한 개발용 절차다.

첫 자연어 검색 Tool은 기존 A05의 `knowledge_search_v1` 설계를 따른다. 입력은 `query`와 허용된 검색 옵션이고 출력은 검색 본문·순위·점수·출처·품질 정보다. 자연어 답변 생성은 A06에서 검색 결과를 Model 채팅 API에 전달하는 단계다.

## 실행 순서와 소유권

1. Agent Tool에 고정한 Knowledge 인덱스 버전·임베딩 공간과 Model 배포 상태를 확인한다.
2. Model의 공식 임베딩 API에 질문 원문을 `role=query`로 보낸다. query prefix·모델 추론은 Model이 담당한다.
3. 응답의 공간·차원·역할·입력 식별자와 벡터를 검증한다. 차원만 같다고 호환되는 것으로 판단하지 않는다.
4. Knowledge 검색 API에 고정한 버전·공간·벡터·허용된 옵션을 보낸다. 후보 생성·필터·선택적 rerank·최종 순위는 Knowledge가 담당한다.
5. 결과와 출처를 보존해 반환하고 ToolCall과 단계별 시간·실패 위치를 연결한다. 중간 벡터는 코드에서 전달하며 LLM 대화 입력에 넣지 않는다.

이 흐름은 정해진 순서로 실행한다. LLM이 매번 임베딩과 검색의 호출 여부·순서를 결정할 필요가 없다. 검색 API·모델 추론을 다른 플랫폼의 DB·OpenSearch·runtime에 직접 접근하는 코드로 대체하지 않는다. 두 API를 먼저 독립적인 공개 Tool로 발행해야만 조합할 수 있다는 제약도 두지 않는다. 내장 어댑터가 각 소유자의 공식 API를 호출하면 된다.

임베딩 실패 시 검색을 실행하지 않는다. 검색 실패·준비되지 않은 버전·공간 불일치는 성공으로 바꾸지 않는다. 정상 빈 결과는 오류와 구분한다. 요청한 rerank 실패 시 자동으로 벡터 검색 성공으로 대체하지 않는다. 실행 중 active 버전이 바뀌어도 이미 선택한 버전은 유지한다. 전체 제한 시간·취소 전파·중복 요청·단계별 재시도 여부는 A05 계약과 검사에 명시하며, 외부 효과가 있는 범용 조합에 무조건 전체 재시도를 적용하지 않는다.

## 조합을 두는 위치

| 위치 | 적용 기준 | 현재 결정 |
|---|---|---|
| Agent 내장 검색 Tool | Agent·MCP·Tool API가 자연어 검색을 제공 | A05의 구현 위치로 유지 |
| Knowledge 자연어 검색 API | 일반 웹·앱 등 여러 호출자가 Agent 없이 같은 검색 기능을 재사용 | 별도 요구가 생길 때 검토. 지금 새 endpoint를 확정하거나 구현하지 않음 |
| Agent 내부 흐름 | 검색 결과를 근거로 답변 생성·추가 도구 사용 | A06의 검색·답변 템플릿 및 후속 확장 |
| n8n 상위 흐름 | 검색·Agent 호출 이후 승인·업무 분기·외부 전달 | 기존 A07 역할 유지 |

Knowledge에 자연어 검색 API를 추가하는 경우에도 모델 추론은 Model이 제공한다. 공통 검색 조합은 Knowledge 한 곳에서 관리하고 Agent Tool은 그 API를 호출하는 어댑터로 정리한다. 동일 조합을 양쪽에 중복 구현하지 않는다. 현재는 기존 API 계약과 플랫폼 경계를 유지하는 A05를 우선한다.

## 서비스 관리와 실행 조합의 구분

| 개념 | 관리 대상 | 예시 |
|---|---|---|
| API 등록 방법 | API 정보를 입력하는 방식 | 직접 URL/schema 입력 또는 OpenAPI 가져오기 |
| 서비스별 API 관리 | 서비스 이름·설명, 환경별 연결·인증 참조, API 목록·명세 버전 | Model 서비스의 임베딩/채팅 API, Knowledge 서비스의 검색 API |
| API 조합 Tool | 여러 호출의 순서·입출력 연결·고정 버전·실패 처리 | Model 임베딩 결과를 Knowledge 검색 입력에 연결 |
| Agent/업무 흐름 | Tool과 모델 호출·분기·결과 전달 | 검색 후 답변 생성, 담당자에게 전달 |

직접 등록과 OpenAPI 가져오기는 유지한다. 한 OpenAPI 문서에 operation이 여러 개 있어도 실행 순서와 데이터 전달이 자동 결정되는 것은 아니다. 서비스 그룹도 실행 순서를 뜻하지 않는다. 하나의 조합 Tool은 여러 서비스의 API를 참조할 수 있다.

서비스별 관리에는 기존 Connection/ConnectionVersion과 인증 참조를 재사용하는 방향으로 설계한다. 개발/운영 연결을 구분하고 발행된 Tool의 연결·API 버전은 고정한다. 서비스 설정을 바꿨다고 기존 발행 Tool의 호출 주소가 조용히 바뀌지 않게 한다. API 목록의 모든 기능을 LLM/MCP에 자동 노출하지 않고, 사용자가 선택해 발행한 Tool을 노출한다. 카탈로그를 다른 플랫폼의 데이터·배포 수명주기를 관리하는 두 번째 원본으로 만들지 않는다.

## 구현 순서와 검증 기준

1. 현재 A04 화면에서 준비된 검색 입력으로 개별 API Tool 등록·시험·게시를 확인한다. 화면 연결과 Gateway 기동만으로 A04 전체 인수를 완료하지 않는다.
2. A05 내장 자연어 검색 Tool을 구현한다. 사용자 시험 화면은 지식 선택 → 질문 입력 → 검색 결과 확인이며 연결·버전·임베딩 설정은 관리자가 확인할 상세 설정으로 둔다.
3. A05 이후 서비스별 API 목록·연결 관리를 작은 범위로 추가한다. A06~A10의 기존 단계 번호와 플랫폼 소유권은 유지하고 세부 일정은 별도 범위로 정리한다.
4. 추가 조합 사례가 생기면 단계별 입력 매핑·오류 처리·실행 기록을 범용 기능으로 확장한다. 임의 그래프 편집·범용 workflow 엔진은 이번 기록만으로 개발 착수·도입이 확정된 것으로 보지 않는다.

A05는 자연어 입력만으로 임베딩 1회와 검색이 연결되는지, 지정한 버전/공간을 사용했는지, 본문/출처가 보존되는지 검사한다. 임베딩 실패·잘못된 공간·검색 실패·정상 빈 결과·rerank 실패를 구분하고 REST/MCP가 같은 Tool 실행 기록을 사용하는지 확인한다. 이 문서 작성으로 기존 인덱스·배포·데이터를 변경하거나 GPU 검사를 반복하지 않는다.

## 근거와 현재 한계

- 프로젝트의 [아키텍처](architecture.md), [A05 Tool 계약](api-tools.md), [작업계획](work-plan.md), [Knowledge 검색 계약](../knowledge-platform/api-search.md)을 확인했다. runtime에는 현재 `openapi_http_v1`과 진단 어댑터가 있고 A05 어댑터는 없다.
- [LangGraph workflows/agents](https://docs.langchain.com/oss/python/langgraph/workflows-agents)는 정해진 순서의 workflow와 동적 agent를 구분한다.
- [Azure AI Search vector query](https://learn.microsoft.com/en-us/azure/search/vector-search-how-to-query)는 호출자가 임베딩을 생성하는 방식과 검색 서비스의 통합 벡터화 방식을 설명한다. 외부 제품의 도입 결정은 아니다.
- 위 공식 자료는 2026-09-23 설명 시 확인했으며 이번 결정은 현재 프로젝트의 경계·재사용 범위에 대한 설계 판단이다.

## 내부 API schema 자동완성 후속

사용자는 검색 Tool 시험 성공 후 개별 schema·ID·벡터 지정이 어렵다는 피드백을 주었다. [자동완성·내부값 자동 연결 요구](schema-autofill-followup-20260923.md)를 기록했다. 등록 화면은 서비스·기능 선택으로 계약 기반 schema를 채우고, A05 시험은 자연어 질문만 받아 내부에서 ID·벡터를 준비한다. 자동완성과 실제 호출값 생성을 구분하며 현재 구현 완료로 표시하지 않는다.
