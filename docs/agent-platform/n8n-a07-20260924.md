## 1. 역할과 이번 범위

n8n은 입력·분기·전달 등 상위 업무 Flow를 편집/실행한다. Agent는 Tool/Agent 정의·버전·실행의 기준 저장소다. LangGraph는 Agent 내부 검색/답변을 실행한다. n8n에는 Agent API 호출용 Header Auth 자격만 연결한다. Model·Knowledge 비밀, Agent 내부 토큰·DB 자격을 복제하지 않는다.

현재 운영 구성 `src/infra/n8n`은 `infrastructure` Compose 이름, 전용 PostgreSQL 16 DB/제한 계정/schema, 전용 볼륨·암호화 키를 사용한다. n8n이 사용하는 uuid-ossp 확장은 최초 DB 관리자 초기화에서 n8n schema에 설치하며 앱 계정에 superuser/DB 생성 권한을 부여하지 않는다. 기본 UI 포트는 16200이다. n8n만 `ops-infra`에서 Agent Gateway를 호출하고, DB는 내부 네트워크에 남는다. 기존 Agent Compose에 n8n을 필수 의존성으로 추가하지 않았다. Model/Data/Knowledge 실행 코드는 변경하지 않았다.

n8n 2.40.5의 공식 이미지와 amd64/arm64 manifest digest를 고정했다. Redis·queue mode·SSO·iframe은 이번 범위가 아니다. 사용자 n8n 계정은 별도로 만들고 로그인한다. n8n 편집기는 신뢰된 개발/사내망에서 사용하는 현재 운영 범위를 따른다.

## 3. 화면을 확인할 수 있을 때

1. `http://<서버IP>:16200`에서 n8n 소유자 계정을 만들고 별도로 로그인한다. 이 단계는 지금 보류해도 된다.
2. Agent `/console`에서 검색 Tool과 Agent를 시험·발행한다. 기존 A06 화면/실제 답변 확인도 이때 함께 진행한다.
3. n8n에서 **Header Auth** 자격을 만든다. 이름은 `Agent Platform API`, Header Name은 `Authorization`, Value는 `Bearer <Agent API 토큰>`이다. 비밀은 워크플로 JSON에 직접 쓰지 않는다.
4. `n8n/workflows/agent-question.json`을 가져온다. 비활성 수동 실행 예제이며 가져오기만으로 검색/모델을 호출하지 않는다.
5. `Question settings`의 AgentVersion ID와 질문을 실제 발행 버전/자료에 맞게 바꾼다. 두 HTTP 노드 `Accept Agent run`, `Read Agent run`에 위 자격을 선택한다.
6. Manual start로 실행한다. `Answer and sources`에서 답변·출처·AgentRun/request/ToolCall ID를 확인한다. Agent가 failed/interrupted이면 `Agent failure`에서 n8n 실행도 실패한다.
7. 원하는 입력·분기·결과 전달 노드를 붙여 Flow를 편집한다. 반복 문의/일정/webhook 활성화는 사용자가 해당 Flow에서 명시적으로 설정한다.

UI 대신 미리 설정한 JSON을 만들 수도 있다. 새 출력 파일을 사용한다.

```bash
python3 n8n/ops/workflow.py \
  --agent-version-id '<발행한 AgentVersion ID>' \
  --question '선택한 자료에서 설명하는 연구 범위는 무엇인가요?' \
  --output ~/workspace/my-agent-flow.json
```

컨테이너 안의 기본 호출 주소는 `http://agent-gateway:8000`이다. 호스트용 `http://127.0.0.1:16100`과 구분한다. Generator의 `--agent-url`은 환경이 다를 때만 바꾼다. 필요하면 `--credential-id`로 n8n 자격의 **참조 ID**만 지정한다. 생성물에는 실제 토큰이 들어가지 않는다.

## 4. 예제 Flow의 동작·재시도

| 노드 | 동작 |
|---|---|
| Question settings | 질문, AgentVersion, Agent Gateway origin |
| Prepare request | 논리 요청 키와 고정 body/caller_context를 만든 뒤 실행 데이터로 저장 |
| Accept Agent run | 동일 키/body로 POST /api/agent-runs. 응답 유실 시 최대 3회 재전송 |
| Run pointer | 202·AgentRun/버전·상대 status URL 검증. 외부 status URL을 따라가지 않음 |
| Read Agent run | 저장된 ID로 GET 조회. HTTP 200만으로 완료 판단하지 않음 |
| Evaluate state / Still waiting / Wait | accepted/running이면 2초 후 재조회. 300회·650초 제한 |
| Agent succeeded | succeeded이면 답변/출처 전달, failed/interrupted/poll_timeout이면 실패 분기 |

전체 n8n workflow timeout은 720초, HTTP 한 번은 8초·최대 3회 시도다. Agent의 더 짧은 deadline은 유지된다. 폴링 제한이 끝나도 Agent가 취소되는 것은 아니므로 저장한 AgentRun ID로 결과를 다시 조회한다. 자동 모델/다른 Agent fallback은 없다. no_evidence는 정상 완료이고 answer_truncated/warnings를 그대로 전달한다.

같은 n8n 실행 안의 HTTP 재시도는 Prepare request 결과를 재사용한다. 새 수동 실행은 새로운 논리 요청이며 새 AgentRun을 만든다. **응답 유실을 복구하려고 새 수동 실행을 그대로 누르면 중복 업무가 될 수 있다.** 먼저 원래 실행의 Run pointer를 확인한다. 접수 ID가 없으면 Prepare request의 `request` 객체(또는 성공 결과의 `replay_request`)를 원문 그대로 파일로 저장해 재사용한다.

```bash
python3 n8n/ops/workflow.py \
  --replay-file ~/workspace/original-agent-request.json \
  --output ~/workspace/recover-agent-flow.json
```

replay 파일에는 invocation_key와 body 전체가 있어야 한다. **원래 caller_context도 유지한다.** 현재 Agent의 멱등 지문에 caller_context가 포함되므로 같은 키에 새 execution_id를 넣으면 409다. 새 n8n 실행의 ID는 결과의 n8n_execution에 따로 남으며 최초 호출자 정보는 original_caller_context로 보존한다. 질문·버전·키를 임의로 섞지 않는다. n8n의 모든 trigger 재전달을 자동 exactly-once라고 보장하지 않는다.

실행 데이터는 n8n에도 저장되며 기본 7일·최대 1,000개로 정리한다. AgentRun/ToolCall은 Agent의 기록이다. 오래된 실행 복구에 필요한 요청 키/ID는 업무 측 보관 정책에 따라 별도로 유지한다. 질문/답변을 포함하는 복구 파일을 소스 저장소에 넣지 않는다.

## 5. Agent 소유 WorkflowLink API

Agent API 토큰으로 등록한 n8n 인스턴스 origin·workflow ID·고정 AgentVersion의 참조를 보관한다. 서버에서 n8n URL을 요청하거나 Flow 정의/비밀을 복사하지 않는다. 등록은 **연결 참조 저장**이며 n8n 실존/접속/실행을 검증했다는 뜻이 아니다.

| API | 역할 |
|---|---|
| POST /api/workflow-links | display_name, instance_url, workflow_id, agent_version_id. Idempotency-Key 필요 |
| GET /api/workflow-links | limit/cursor 목록 |
| GET /api/workflow-links/{id} | 참조·파생 edit_url·revision 조회 |
| PATCH /api/workflow-links/{id} | expected_revision과 display_name/enabled 변경 |

생성 시 활성 Agent의 발행 버전만 허용한다. instance_url은 사용자 정보/query/fragment/path가 없는 HTTP(S) origin이고 workflow ID는 영문·숫자·밑줄·하이픈만 허용한다. edit_url은 `/workflow/{id}`로 구성한다. 같은 인스턴스/워크플로 중복 등록은 409, 같은 멱등 요청은 원래 참조를 재현한다. enabled=false는 Agent 쪽 링크 사용 중지이며 n8n Flow를 중지/삭제하지 않는다. 반대로 n8n에서 버전/Flow를 바꿔도 AgentLink가 자동 갱신되지 않는다. 새 버전의 Flow는 별도 workflow ID로 등록한다.

CLI는 서버에서 화면 없이 참조를 등록할 수 있다. 실제 n8n workflow ID와 발행 AgentVersion ID가 있을 때 실행한다.

```bash
python3 n8n/ops/register_link.py \
  --instance-url 'http://<서버IP>:16200' \
  --workflow-id '<n8n workflow ID>' \
  --agent-version-id '<발행 AgentVersion ID>' \
  --name '문서 질의응답 Flow' \
  --state-file ~/workspace/my-flow-link.json
```

등록·조회와 실행 연결 기반이 이번 범위다. Agent 화면에서 Flow 링크를 새 탭으로 여는 통합 관리 UI는 A08에서 제공한다. 지금 화면 확인을 위해 개발을 멈추거나 임의 사용자 계정을 생성하지 않는다.

## 6. 검증·남은 인수

아래 로컬 기능 검사는 모두 통과했다. Go 전체 패키지·Python Runtime 42/기존 ops 15·n8n ops 6/코드 계약 6·기존 DOM 59개를 확인했다. 실제 Compose 2.39.4 정규화와 비밀/DB 네트워크/socket/공개 포트 경계 검사도 통과했다. n8n DB 초기화 SQL의 uuid-ossp 선설치는 공식 n8n TypeORM 요구를 반영했으며 native PostgreSQL 기동 검증은 서버에서 확인한다.

- 공식 n8n 2.40.5 **실제 CLI 실행기**와 격리 SQLite/HTTP 대역으로 응답 유실 재전송, 폴링, 답변/출처, 새 실행에서 원래 요청 재사용, 키 충돌, no_evidence, failed/interrupted 분기를 검사한다.
- 실제 n8n→Agent REST→Go/Python gRPC→Agent SQL→HTTP Model/Knowledge 대역 경로를 검사하고, 새 n8n execution에서 같은 요청 재사용 시 추가 채팅이 발생하지 않는지 확인한다.
- WorkflowLink의 생성·재조회·동일 키·중복/변경 충돌·revision·초안 거절·URL 경계와 기존 Agent/Tool/OpenAPI/Knowledge 회귀를 검사한다.
- 코드/설정 검사는 실제 Docker 이미지 실행과 구분한다. 로컬 n8n 검사 DB는 SQLite, Agent SQL은 PGlite이며 사용자 서버 n8n PostgreSQL 기동/검사는 위 명령의 별도 인수다.
- 사용자 n8n 계정·Flow 편집/저장/실행 화면, 실제 준비된 LLM/지식 답변, 재시작 후 실제 실행/자격 보존 확인은 보류 항목이다. A07 전체 서버/사용자 인수나 A08 UI 완료로 표시하지 않는다.
