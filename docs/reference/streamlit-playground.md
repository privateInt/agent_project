# Streamlit 모델 관리·학습·배포 콘솔

Docker 단일 서버의 기존 Gateway API를 버튼으로 직접 사용하는 Streamlit 화면이다. 상단 메뉴는 관리·채팅 두 개다. 관리에는 모델 → 배포된 모델 → 데이터셋 → 학습 작업을 세로로 배치한다. 모델 관리 위쪽에서 ‘모델 조회’를 누르면 각 행에 관리 이름·Hugging Face 원본·버전 선택·배포·학습·삭제 버튼이 보인다. 바로 아래 배포 목록에서 조회·채팅·종료한다. 모델 이름을 누르면 상세와 이전 버전 조회를 펼친다. 채팅은 이미 배포된 모델을 선택하는 별도 화면이다. 사용자가 UUID를 복사해 입력할 필요가 없다.

## 시안 기준 화면 구성

기존 사이드바·카드 배치를 상단 메뉴와 공통 열 제목을 가진 표로 재구성했다. 모델 관리 도구 모음에는 모델 조회·이름 검색·종류 필터·모델 추가가 한 줄에 있다. 아래 모델 표의 열은 등록 이름 / Hugging Face 원본 / 사용할 버전 / 상태 / 작업이다. 상태는 색상 배지, 실행은 각 행의 배포·학습·삭제 버튼으로 제공한다. 버전 선택란은 버전 이름만 보여주며 상태는 별도 열에 표시한다.

HF 원본 아래에는 요청 revision과 확정 커밋 앞 12자리를 간략히 표시한다. 학습 결과는 기반 원본 커밋을 표시한다. 전체 revision·원본 연결과 설명은 모델 이름으로 여는 상세에서 확인한다. 초기 조회는 계속 명시적인 버튼 동작이며 검색어 입력만으로 조회하거나 실행하지 않는다. 이전/다음과 현재 페이지 건수는 표 아래에 있다. 서버가 총 건수를 제공하지 않으므로 전체 모델 개수로 표시하지 않는다.

아래 배포 목록에도 같은 열 폭·표·상태 배지와 조회·채팅·종료 버튼을 적용했다. 실행 폼/삭제 확인은 클릭한 행 아래에만 열린다. 모델/데이터셋 추가의 통합 폼, API·버전 고정·멱등 재시도와 옛 URL은 유지한다. 목업의 예시 모델·커밋·사용자 이름을 실제 화면 데이터로 넣지 않는다.

표현은 기존 Streamlit 1.63.0 기본 위젯과 고정 CSS를 사용한다. 모델 이름·원본 정보를 HTML에 삽입하지 않고 Streamlit 텍스트로 출력한다. 추가 외부 폰트·JavaScript·프론트엔드 의존성은 없다. CSS는 현재 버전의 컨테이너 키와 위젯 구조에 맞추었으므로 Streamlit 업그레이드 때 화면을 확인해야 한다. 데스크톱 표를 기준으로 하며 좁은 화면에서는 기본 열 줄바꿈을 허용한다. 실제 브라우저 시각 검증은 아직 수행하지 않았다.

## 관리 영역과 채팅 기능

| 영역 | 조회·선택 | 직접 실행하는 버튼 |
|---|---|---|
| 모델 관리 | 모델 검색·종류 필터·이전/다음 페이지, 모델과 버전 상세 | 모델 추가(이름+Hugging Face 저장소), 기존 모델의 버전 추가, 선택 버전 학습·배포·목록 삭제, 아래 배포 조회·종료 |
| 데이터셋 | 이름 검색, 데이터셋·버전 목록과 내용 식별 정보 | 데이터셋 추가(이름+JSONL 파일), 기존 데이터셋의 파일 버전 추가, 예제 다운로드 |
| 학습 작업 | 상태별 목록, 진행 상태·Operation, 로그·평가·비교·체크포인트·출력 조회 | 취소, 체크포인트에서 새 학습, 완료 출력 업로드 재시도, 결과 모델 열기 |
| 배포 관리 | 상태별 목록, 선택한 배포 진행 상태·Operation | 배포 중지, 준비된 배포와 채팅 화면으로 이동 |
| 채팅 | 준비된 배포 목록에서 모델 이름·버전으로 선택 | 질문·예제 질문 전송, 새 대화, 관리에서 배포 보기 |

조회 버튼과 페이지 이동·선택·상태 갱신은 GET만 사용한다. 목록은 10개씩 조회하고 조회 당시 필터와 커서를 보존해 이전/다음 페이지를 이동한다. 모델 목록은 items/next_cursor, 데이터셋 목록은 datasets 또는 versions/next_after_id 계약을 따른다. 선택 모델 버전은 3초, 열린 학습 상세 팝업은 5초, 열린 배포 상세 팝업과 채팅은 3초 간격으로 상태를 조회한다. 배포·데이터셋·학습 상세는 관리 화면 아래에 상시 출력하지 않는다. 배포 조회 버튼 또는 데이터셋·학습 이름으로 해당 상세 팝업을 연다. 닫기·화면 이동 뒤에는 상세 조회를 중단하며, URL의 선택 ID만으로 팝업을 자동 복원하지 않는다. 목록·필터·페이지와 보류 요청은 보존한다. 로그·평가·체크포인트·출력은 해당 조회 버튼으로 갱신한다.

모델 이름을 클릭한 뒤 ‘버전 조회’로 버전을 선택한다. LLM의 ready snapshot은 학습과 배포, ready adapter는 배포가 가능하다. embedding/reranker/OCR은 기존 관리 API의 등록·조회·가져오기를 연결하며 해당 모델의 학습/배포 엔진을 새로 추가한 것은 아니다.

## 한 번에 추가하기

‘모델 추가’ 버튼을 누르면 팝업에서 등록 이름과 Hugging Face 저장소를 같은 폼에서 입력한다. ‘모델 추가하기’ 한 번으로 관리 항목 생성과 첫 버전 가져오기를 순서대로 요청한다. HF 토큰은 기본 입력란에 두고 모델 종류·버전 이름·revision·설명은 추가 옵션에 둔다. 기본값은 llm/base-v1/main이다. 성공 안내는 가져오기 요청 접수를 뜻하며 다운로드 완료는 선택 버전의 상태로 확인한다.

‘데이터셋 추가’도 팝업에서 이름과 JSONL 파일을 같은 폼에서 입력하고 ‘데이터셋 추가하기’ 한 번으로 항목과 첫 파일 버전을 추가한다. 기본 버전은 v1이며 설명은 추가 옵션이다. 이름·저장소/파일 등 필수 입력과 파일 크기를 확인한 뒤 첫 API 요청을 보낸다. 전체 JSONL 검증은 기존 서버가 담당한다.

이미 있는 항목에 추가할 때는 모델 상세의 ‘이 모델에 다른 버전 추가’ 또는 데이터셋 상세의 ‘이 데이터셋에 새 파일 버전 추가’를 사용한다. 부모 항목을 다시 등록하지 않는다. 새 항목은 목록 위의 팝업에서 추가한다. 닫기/ESC/X/바깥 클릭은 팝업만 닫고 기존 목록·필터·페이지를 유지한다. 이미 접수된 작업과 응답 유실 기록을 취소하지 않는다. 한 번에 하나의 팝업만 열며, 모델 추가 접수 후에는 모델 상태로, 데이터셋 추가 완료 후에는 해당 데이터셋 상세 팝업으로 연결한다.

## 관리 이름과 Hugging Face 원본 구분

관리 이름은 플랫폼에 등록한 별칭(e2e-model-1788416939 등)이며 수정하지 않는다. 모델 행의 제목은 관리 이름이고, 함께 표시하는 원본은 그 행에서 선택한 버전 기준이다. 버전 선택은 최근 100개를 제공하며 처음에는 가장 최근 등록 버전을 선택한다. 이전 버전은 모델 이름을 눌러 상세의 페이지네이션으로 조회한다. 모델 검색은 계속 관리 이름·설명 기준이다.

| 화면 표시 | 저장된 값 | 의미 |
|---|---|---|
| 관리 이름 | Model.name | 플랫폼 안에서 관리할 때 쓰는 이름 |
| 플랫폼 버전 | ModelVersion.version | 가져온 버전 또는 학습 결과에 붙인 플랫폼 이름 |
| Hugging Face 원본 | repo_id | 원본 저장소명, 예: google/gemma-3-1b-it |
| 요청 버전 | requested_revision | 가져올 때 지정한 브랜치·태그·커밋 |
| 확정 버전 | resolved_revision | 실제로 내려받은 원본을 식별하는 커밋. 요약은 앞 12자리, 펼치면 전체 값 |

학습 결과에는 ‘기반 Hugging Face 원본’이라고 표시한다. source_model_version_id로 연결된 원본을 조회하며 임의의 최근 버전을 기반 모델로 사용하지 않는다. 원본 연결 누락·조회 실패·순환·잘못된 응답 ID는 ‘확인하지 못함’으로 표시한다. 없는 revision을 main으로 채우거나 미확정 버전을 확정한 것처럼 보이지 않는다. 자동 생성된 train-UUID 버전은 ‘학습 결과 · 짧은 ID’로 요약하고 상세에는 전체 등록 버전 이름을 남긴다. DB 이름·버전·요청 ID는 변경하지 않는다.

학습 목록·배포 목록·채팅에도 같은 원본 정보를 표시한다. 현재 REST의 버전 상세에 repo_id/requested_revision/resolved_revision이 모두 있으므로 API·DB 수정 없이 연결한다. 표시에 필요한 정보만 세션별 최대 256개·60초 동안 캐시하고 목록 조회 버튼에서 비운다. 런타임 상태·실행 가능 여부는 기존처럼 새 GET 응답으로 판단하며 실행 대상은 사용자가 선택한 버전 ID로 고정하고 버튼을 누를 때 최신 상세를 검증한다. 이 원본 표시는 저장된 기록 조회이며 외부 Hugging Face의 최신 상태 조회가 아니다.

## 모델 목록 삭제와 배포 종료

`DELETE /api/models/:id`는 models.deleted_at을 기록하고 해당 모델과 그 버전들을 목록 API에서 제외한다. 동일 UUID로 반복해도 최초 삭제 시각이 유지된다. 응답은 모델 정보와 deleted_at이며, 없는 UUID는 404, 잘못된 UUID는 400이다. UI는 대상 관리 이름과 모든 버전에 적용됨을 확인한 뒤 DELETE하고, 응답 ID/삭제 시각을 확인해야 목록에서 지운다.

이는 카탈로그 정리 기능이다. 모델/버전 DB 행과 MinIO 파일·캐시·학습 이력은 보존하며 저장 공간을 확보하지 않는다. 기존 UUID의 상세 조회는 원본 추적과 실행 이력을 위해 계속 지원한다. 이미 접수된 가져오기·학습·배포는 계속되고 학습 결과 게시도 막지 않는다. 같은 등록 이름은 이력과 함께 남으므로 다른 모델에 재사용할 수 없다. 목록 복구 API는 아직 없다.

삭제 뒤 새로운 가져오기는 거절하며, 삭제 전에 접수한 동일 키의 가져오기 재요청은 원래 결과를 반환한다. 새 가져오기와 삭제는 모델 행 잠금으로 순서를 결정한다. UI는 캐시된 목록의 배포·학습 버튼을 눌러도 새 상세 GET으로 삭제 여부/선택 버전을 확인한다. 이 카탈로그 삭제가 이미 알려진 버전 UUID를 사용하는 모든 내부/직접 API 실행을 차단하는 접근 제어는 아니다.

배포 목록의 ‘조회’는 해당 배포의 현재 상태를 GET으로 갱신하고 상세 팝업을 연다. ‘종료’는 대상 배포 이름·짧은 ID를 확인한 뒤 기존 `POST /api/deployments/:id/stop`을 사용한다. 다른 배포를 함께 종료하지 않는다. 조회·페이지 새로고침·확인 창 열기에는 변경 요청이 없다. DELETE 또는 stop 응답이 끊기면 자동으로 재전송하지 않고 같은 대상의 확인 버튼으로 다시 요청한다. 모델 목록 삭제와 배포 종료는 서로 별도 동작이다.

## 쉬운 기본 화면과 고급 설정

학습 폼은 데이터 선택·학습 단계 수부터 보여준다. GPU·입력 길이·배치·누적·학습률·LoRA·체크포인트는 기본적으로 접힌 고급 학습 설정에 둔다. 배포 GPU·문맥 길이·메모리 비율도 고급 배포 설정에 둔다. 접힘 여부와 무관하게 위젯 값과 기존 요청 기본값을 유지한다. 1단계 학습은 실행 확인용임을 안내한다.

모델 종류·상태 필터·진행 상태를 한국어로 표시하며 원래 API 코드는 상세에서 볼 수 있다. 학습/배포 버튼 아래에 목적과 다음 화면을 설명한다. 원본은 새 학습을 시작할 수 있고, 이미 학습한 결과는 배포해 대화할 수 있음을 안내한다. 데이터셋 표에서는 대화 예시 수·파일 크기를 보여주고 긴 해시는 상세로 옮겼다.

## 학습과 데이터 업로드

학습에서는 등록된 chat_messages 데이터셋의 ready 버전을 선택하거나 내장 테스트 데이터를 사용할 수 있다. 등록 버전은 dataset_version_id로 고정한다. 평가를 켜면 별도 버전을 선택해야 하며 학습 데이터와 SHA-256이 같으면 요청하지 않는다. 서버가 입력과 버전 무결성을 최종 검증한다.

QLoRA 단일 GPU, sample_packing=false를 사용한다. 기본값은 1 step, sequence_length=256, micro_batch_size=1, gradient_accumulation_steps=1, learning_rate=0.0002, LoRA r=8/alpha=16/dropout=0이다. GPU·단계 수·입력 길이·배치·누적·학습률·LoRA·checkpoint_steps는 화면에서 조정한다. GPU 번호 기본값은 MODEL_PLAYGROUND_GPU_ID(기본 0)이며 자동 GPU 선택이나 원격 실행은 하지 않는다.

데이터셋 이름과 첫 파일 업로드는 한 폼·한 번의 추가 버튼으로 연결한다. 서버 API는 기존 등록/업로드 계약을 유지한다. 업로드는 최대 64 MiB JSONL이며 version/file 두 multipart 필드만 전달한다. 전송 파일명은 dataset.jsonl이고 내용 바이트는 그대로 보존한다. 전체 JSONL 검증·MinIO 저장/readback·불변 버전 판단은 기존 Training API에서 한다. 같은 내용의 재요청은 원래 버전을 돌려준다.

체크포인트 재개는 checkpoint_step을 지정하는 새 학습 요청이다. 완료 출력 업로드 재시도는 보존된 결과 업로드만 수행한다. 이 버튼들은 원래 실패/취소 이력을 수정하지 않는다. 취소는 완료 응답까지 상태로 확인한다.

## 배포와 채팅 분리

‘배포 설정’에서 GPU·문맥 길이·GPU 메모리 비율을 선택하고 ‘배포 시작’을 누른다. 기본값은 GPU 0, vLLM, max_model_len=2048, gpu_memory_utilization=0.5다. 요청 후 배포 상세 팝업에서 준비·시작·ready 또는 메모리 부족 등의 실패를 확인하고 ‘이 배포와 채팅’으로 이동한다. 채팅 페이지 자체에는 새 배포·학습 버튼이 없다.

‘새 대화’는 대화 기록만 비운다. 다른 배포를 선택하면 이전 대화를 새 모델에 보내지 않도록 기록을 비운다. 배포 중지는 관리 화면에서 수행하며 stopped 상태를 확인한다. 브라우저를 닫아도 실행은 계속된다. 같은 배포를 사용하는 다른 사용자도 중지의 영향을 받는다.

## 응답 유실과 재요청

생성 버튼을 누를 때 UUID 멱등 키와 입력 SHA-256을 만들고, 전송 전에 URL의 pending 값에 v2 요청 기록을 남긴다. 기록에는 작업 종류·대상 ID·키·해시만 넣고 HF 토큰·업로드 원문·대화는 넣지 않는다. 실제 본문과 파일은 현재 서버 세션 메모리에만 보관하고 성공하면 요청 사본을 비운다. 가져오기 성공 시 토큰 입력도 비운다.

응답 유실/오류에서는 자동 POST 재시도를 하지 않는다. 같은 세션의 ‘같은 요청 다시 확인’은 원래 키와 고정 입력을 재사용한다. 상세 팝업을 닫아도 보류 요청은 남는다. 새 세션의 ‘요청 화면으로 이동’은 사용자 클릭 뒤 해당 업로드·학습 복구 상세 팝업을 연다. 새 브라우저 세션에서는 원래 화면에 같은 값·파일·HF 토큰을 다시 입력하고 실행 버튼을 누른다. 입력 해시가 다르면 HTTP 요청 전에 거절한다. 원래 요청의 결과를 관련 목록에서 확인한 뒤에만 요청 기록을 닫고 새 입력을 보낼 수 있다. GET으로 결과를 확인할 수 있도록 화면 이동은 유지한다.

통합 추가는 내부적으로 두 API 호출이며 하나의 DB 트랜잭션은 아니다. UI 요청 키에서 UUIDv5로 등록용 키와 버전용 키를 각각 고정한다. 등록 응답의 ID를 확인해야 두 번째 호출을 진행한다. 어느 응답이 유실돼도 ‘추가 이어서 진행’은 같은 두 키를 재사용한다. 등록 API를 다시 호출해도 멱등 응답의 기존 항목을 받아 이어서 처리한다. URL에 보이는 ID를 두 번째 요청 대상으로 신뢰하지 않고 등록 응답을 다시 확인한다.

두 번째 단계가 실패하면 이미 만들어진 항목은 남고 선택 정보에 보존된다. 자동 삭제·자동 재시도는 하지 않는다. 새 세션에서는 같은 통합 폼을 열어 원래 값·파일·토큰을 다시 입력한다. 입력을 바꿔야 한다면 기존 결과를 목록에서 확인하고 요청 기록을 닫은 뒤 그 항목의 버전 추가에서 수정한다. 비동기 가져오기 요청 접수 뒤 Job이 실패한 경우도 기존 모델의 새 버전 추가를 사용하며, 완료된 과거 요청을 자동 재실행하지 않는다.

기존 v1 request URL은 고정된 옛 배포 본문과 키를 복원하며, 사용자 확인 버튼 전에는 전송하지 않는다. 기존 deployment URL은 해당 배포의 채팅 화면을 연다. 대화는 session state에 보관되므로 앱 재시작·브라우저 새 세션에서 사라질 수 있다. 채팅 실패는 ‘같은 질문 다시 보내기’로 명시적으로 재전송하며 새 추론을 수행한다.

## 채팅 REST 계약

`POST /api/deployments/:id/chat` — 준비된 로컬 vLLM 배포에 일반 텍스트 채팅을 전달한다. 새 Operation/Job을 생성하지 않으며 토큰 streaming은 제공하지 않는다.

```json
{
  "messages": [{"role": "user", "content": "안녕하세요"}],
  "max_tokens": 256,
  "temperature": 0.7
}
```

- 필드는 정확히 messages, max_tokens, temperature만 허용한다. 중복 키·잘못된 대소문자·알 수 없는 필드·null·추가 query를 거절한다.
- messages는 1..33개다. 선택적인 첫 system 뒤 user/assistant가 번갈아 나오고 마지막은 user여야 한다. 각 항목은 role/content 문자열만 받으며 빈 content는 거절한다.
- 요청은 UTF-8 최대 64 KiB, 전체 메시지 최대 16,000자다. Streamlit의 새 질문은 최대 4,000자다.
- max_tokens는 기본 256, 1..512 정수다. temperature는 기본 0.7, 0..1.5다. 화면은 답변 길이 128/256/512, 다양성 0..1.2로 제공한다.
- 이미지·오디오·도구 호출·추가 generation 옵션은 받지 않는다. 모델의 실제 토큰 문맥 한도는 vLLM이 검사한다.
- status/runtime_state=ready, desired_state=running, engine=vllm인 현재 배포만 전달한다.
- 내부 주소는 해당 ID의 `http://model-serving-{deployment_id}:8000/v1`와 일치해야 하고 model은 `deployment-{deployment_id}`로 고정한다. 호출자가 endpoint/model을 지정할 수 없다.
- HTTP redirect와 환경 HTTP proxy를 사용하지 않는다. vLLM의 응답 model도 동일한 이름이어야 한다. base alias만 응답하면 실패로 처리한다.

성공 응답은 다음 모양이다.

```json
{
  "deployment_id": "d8be0fc3-6231-4a89-9360-78fc7404deaa",
  "model": "deployment-d8be0fc3-6231-4a89-9360-78fc7404deaa",
  "content": "Hello!",
  "finish_reason": "stop",
  "usage": {"prompt_tokens": 15, "completion_tokens": 3, "total_tokens": 18}
}
```

finish_reason=length이면 길이 한도에 도달했다고 화면에 표시한다. 이 예는 응답 형식이다. Gateway 채팅은 기존 서버 GPU smoke에서 별도로 검증했다. Gateway는 vLLM의 오류 본문·내부 경로를 그대로 사용자 화면에 전달하지 않는다.

| HTTP / code | 처리 |
|---|---|
| 400 / INVALID_CHAT | 잘못된 메시지·필드·크기. 입력을 수정한다 |
| 400 / CHAT_INPUT_REJECTED | vLLM이 문맥 길이 등 입력을 거절. 짧게 입력하거나 새 대화 |
| 409 / DEPLOYMENT_NOT_READY | 준비 중·종료·상태 변경. GET으로 현재 상태 확인 |
| 502 / INVALID_RUNTIME_IDENTITY | 저장된 로컬 endpoint/model 이름 불일치. 추론하지 않음 |
| 502 / INVALID_INFERENCE_RESPONSE | 다른 모델·빈 응답·잘못된 형식. 성공 응답으로 표시하지 않음 |
| 503·502 / INFERENCE_UNAVAILABLE | 연결/런타임 오류. 상태를 확인하고 명시적으로 재전송 |
| 504 / INFERENCE_TIMEOUT | Gateway 추론 시간 초과. 자동 재전송하지 않음 |

Gateway→vLLM HTTP 요청 제한은 120초, Streamlit의 채팅 응답 대기는 135초다. 같은 순간 종료 요청이 들어오면 채팅이 실패할 수 있으며 재시작하지 않는다. 채팅 요청 자체에 멱등 저장소는 없으므로 명시적 재전송은 새 추론이다.

## 배치와 검증 범위

브라우저 → Streamlit 서버 → Gateway REST 구조다. Gateway가 현재 배포를 확인하고 내부 Docker 네트워크의 vLLM으로 채팅을 전달한다. UI는 Docker 소켓·GPU·모델 볼륨·DB/MinIO 자격증명 없이 실행한다. 기존 인증 없는 신뢰된 개발/사내망 전제를 따른다. 계정·사용자별 소유권·대화 영속 저장·자동 유휴 종료·물리적인 모델 파일 삭제·목록 복구 기능은 이 변경에 포함하지 않는다.

별도 Python 3.12/Streamlit 1.63.0 이미지, Compose playground profile, 호스트 포트 13100을 유지한다. 진행률 코드를 바꾸면 Operation·Gateway·Playground·Management Import Job의 영향을 확인한다([검사 절차](../testing/model-management-update.md#import-progress)). 화면만 바꾸면 Playground만 재빌드한다. Operation 시작 시 진행률 컬럼을 추가한다. 상세 전송량은 새 이미지로 시작한 import부터 제공한다. 학습 Job·vLLM 이미지는 변경하지 않는다. 소스 COPY --chmod=0644와 USER playground 뒤 UID 10001 읽기 검사를 유지한다.

최신 화면은 서버 AppTest 35개를 통과했고 관련 API 변경도 서버 Go/DB에서 확인했다. API·파일 위젯은 대역이므로 실제 브라우저의 표시·타이머 및 다운로드 관찰과 구분한다. 과거 구현별 검사 수는 [변경 이력](../history/model-platform-202609.md)에 두고 현재 상태는 [프로젝트 상태](../status.md)를 따른다.


## 실제 다운로드 진행률

Operation의 progress는 선택적인 TransferProgress이며 progress_updated_at은 해당 표본의 서버 저장 시각이다. stage(downloading/uploading/stored), current_file, bytes_completed, bytes_total, files_completed, files_total, sequence를 제공한다. bytes_total=0은 미상 또는 빈 파일이다. 값이 없는 옛 Job에 임의의 0~100%를 만들지 않는다.

파일 다운로드 중에만 바이트 기반 퍼센트를 표시한다. 전체 작업 비율은 아니며, 업로드는 상태만 보여준다. MinIO Put 성공 후 files_completed를 올리고 전체 파일 이후 manifest와 모델 등록까지 완료되어야 succeeded/ready다. 실패에는 마지막 표본을 보존한다. 상태 갱신은 선택한 작업의 GET이며 폼/추가 요청을 자동 제출하지 않는다. 가져오기 완료/실패로 바뀌면 실행 버튼 갱신을 위해 전체 화면을 한 번 갱신하되 추가 또는 상세 팝업이 열린 동안에는 이를 보류한다.

UpdateOperationRequest.progress(field 5), Operation.progress(field 27), progress_updated_at(field 28)을 추가했다. 기존 필드는 재번호화하지 않았다. 새 progress 보고는 UpdatePhase와 같은 실행 token/instance로 승인된 running import만 허용한다. 순서가 같거나 낮은 sequence는 최초 저장 시각을 보존하며, writing_manifest/terminal 상태 이후 보고는 거절한다. 최신 표본 하나를 JSONB로 저장하며 이벤트 이력을 증가시키지 않는다.

Import Job은 실제 다운로드에서 tmp/해시에 쓴 바이트를 세고 약 3초 간격 및 단계 전환 시 보고한다. 수치 보고는 2초 RPC 제한·실패 후 30초 backoff이며 다운로드의 재시도/중단 정책을 바꾸지 않는다. 새 이미지로 시작한 Job부터 제공한다. 정확한 전송량을 제공하지 않는 학습 단계에 다운로드 퍼센트를 재사용하지 않는다.

관리 이외 옛 datasets/training/deployments URL은 같은 관리 화면으로 정규화한다. 선택된 모델/버전/데이터셋/실행/배포 ID와 pending 멱등 요청은 보존한다. 채팅의 상태·대화 격리는 유지한다.

## 채팅 모델 구분 (2026-09-16)

**대화 가능한 배포 조회**는 ready/running vLLM 중 일반 채팅 프로필(빈 profile)이고 모델 메타데이터의 model_type=llm을 확인한 배포만 표시한다. Surya OCR의 엔진도 vLLM이므로 엔진만 비교하던 조건을 수정했다. 알 수 없는 프로필·모델 종류 조회 실패도 대화 대상으로 추정하지 않는다. 기본/학습 adapter LLM은 같은 조건으로 표시한다.

OCR 배포는 관리 목록에 계속 나타나고 준비된 상태는 글자 인식용으로 안내한다. OCR의 기존 채팅 URL을 열어도 질문/예제/재전송을 활성화하지 않는다. OCR 선택은 [데이터 관리](../data-platform/testing-console.md#ocr-모델-조회선택)에서 한다. 이번 수정은 모델/데이터 화면 코드이며 채팅 HTTP API의 계약이나 모델 실행 이미지를 바꾸지 않는다.

## 모델 파일 영구 삭제와 GPU 메모리 실패 표시

모델 행의 삭제 확인창에서 목록 삭제 또는 모든 버전 파일 영구 삭제를 선택한다. 영구 삭제는 확인 체크가 필요하고, 배포·학습을 자동 중지하지 않는다. 중지되지 않은 배포/학습은 삭제를 막으며 실패한 요청은 같은 모델에서 재시도한다. 숨긴 모델은 필터의 `목록에서 삭제한 항목 포함`으로 조회한다. 자세한 파일 범위는 [카탈로그](catalog.md)의 영구 삭제 계약을 따른다.

모델 배포는 이미 사용 중인 GPU에도 로딩을 시도한다. GPU 메모리가 부족해 종료되면 `GPU 메모리 부족`으로 표시하며 설정을 바꿔 새 배포를 요청하도록 안내한다.

## K03 임베딩 용도 표시

지원하는 snowflake 원본 또는 명시적 임베딩 profile은 배포 목록에 `임베딩`을 표시하고 상세에 query/document 입력 폼을 제공한다. 입력·버튼 클릭 시 Model profile을 먼저 조회하고 그 공간 ID로 공식 API를 호출한다. 목록/상세 조회와 자동 새로고침은 추론을 실행하지 않는다. 등록 model_type이 llm인 기존 snowflake도 채팅 목록에서 제외한다. [임베딩 계약](embedding.md), [검사](../testing/embedding.md)를 따른다.
